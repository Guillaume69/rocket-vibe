# WORKSTREAMS: the debt found by the audit

From the audit of **25 July 2026** (`docs/AUDIT.md`, commit `50c00dc`): 122 raw
findings, 7 demolished by adversarial refutation, **115 kept**, grouped into 16 workstreams.

- **`docs/AUDIT.md`** holds the detail of each line: the mechanism, the failure scenario, the
  proposed fix, and why a given finding was dismissed. It is no longer touched: it is a dated record.
- **This file** holds the order and the state. This is the one that gets ticked.

## The loop

One workstream = one or more commits. For each:

1. Open `docs/AUDIT.md` at the workstream's section: the fix is already written and weighed there.
2. Fix, starting with the test when the workstream calls for it (it is noted).
3. `npx tsc --noEmit` + the test suite. **On this machine (Node 22)**: `node --test --experimental-strip-types "lib/**/*.test.ts" "db/**/*.test.ts" "ui/**/*.test.ts" "providers/**/*.test.ts"`. `npm test` fails for an environment reason, not a code one.
4. Tick, commit, push.
5. What gets dismissed is struck through (`~~...~~`) with the reason at the end of the line, not deleted.

The order is ranked by **gain over regression risk**, not by severity: a high-gain, zero-risk
workstream goes before a medium-gain, high-risk one. Dependencies between workstreams are
noted; outside them, pick freely.

## 5. Room catch-up: one per room, caches that do not lie

**🟡 medium** · fix risk **medium** · effort **day** · 5 findings

> On EVERY connection setup (hence every return to the foreground) two identical paginations go out on the open room: the provider (guard `rattrapageSalonEnVol`) and the screen, woken by the `generation` bump that this same connection setup has just made, which calls `lib/catchUp.ts` directly without consulting the guard. Up to 8 `chat.syncMessages` where 4 suffice, on a route limited to 10 calls/min and costing 3-4 s per call on the target server. The fix fits in lib/catchUp.ts, without changing a single caller signature. Three neighbouring coverage defects (guaranteeing read swallowed, cache repopulated after purge, thread with no guard) are handled in the same stroke.

**Order.** Assumes the `generation` fix from workstream 1 is in.

- [x] 🟡 Two concurrent catch-ups on the same room at every connection setup - `lib/catchUp.ts:227` → per-room serialization INSIDE `lib/catchUp.ts`, at the only point where all paths meet. No caller signature touched.
- [x] 🟡 The read that GUARANTEES is swallowed for the active room by the anti-stacking guard - `ui/sync.tsx:298` → the provider's guard is removed; a request arriving after a pass has started gets its own, chained behind.
- [x] 🟡 `keepWarm` can repopulate the LRU AFTER `releaseHotRooms`, and the ghost entry makes `roomCovered` lie - `ui/sync.tsx:420` → session token (`ui/sessionToken.ts`), captured on mount, returned on unmount; if it has changed, release instead of remembering. Same treatment for `markRoomLoaded`.
- [x] 🟡 The thread screen re-downloads the WHOLE thread at every connection setup, with no guard or indicator - `app/thread/[id].tsx:197` → `ui/loadedThreads.ts` (guard per generation, like rooms) + `activity.track` + a `SyncBar` under the native header.
- [x] ⚪ `activeRoom` assumes only one room screen is mounted - `app/room/[rid].tsx:366` → `ui/openRooms.ts`, one stack per session; `declareOpenRoom(rid)` returns a way to withdraw, the top is the catch-up target.
- [x] **Workstream exit**: clean `tsc`, 584 tests / 114 suites green (against 557), clean eslint on the 13 touched files, and real launch on the Pixel

> **Deliberate deviation no. 1: the provider's guard is REMOVED, not doubled.** The audit proposed leaving `rattrapageSalonEnVol` in place and removing it later. Impossible: IT is what swallows the guaranteeing read (finding 2), and it does so before even reaching the serializer. Both findings are therefore fixed by a single mechanism, in a single place.

> **Deliberate deviation no. 2: one mechanism instead of "coalesce" + "re-request".** The audit described a coalescing (finding 1) and then a `redemande` flag on top (finding 2). The two requirements are contradictory, and the rule that arbitrates between them fits in one line: **merge into a pass that has not yet read its cursor, otherwise get a fresh one**. A request arriving before the start is covered by the departing pass; one arriving after is not, and deserves its own. Real cost: the chained pass restarts from the cursor the previous one has just advanced, hence an almost empty response. A test pins it (`next=1000` then `next=1500`).

> **Deliberate deviation no. 3: the thread's activity scope = `threadId`, not `rid ?? threadId`.** `rid` is unknown when loading starts (thread opened by direct link: the root is not in the database yet) and appears DURING the fetch. The bar would have listened to a scope nobody fed. `threadId` is stable from the first render.

> **Method note.** Each fix was proven BY REMOVAL: serialization taken out → 5 failures; `every` over the discards reduced to the first requester → 1 targeted failure; the three token guards removed and the stack reduced to `pop()` → 6 failures. None of these tests is empty.

## 6. Lifecycle of local data: purge, cursors, retention

**🟡 medium** · fix risk **medium** · effort **day** · 4 findings

> The purge knows only three tables out of eight, cursors outlive the data they describe, and the purge criterion is a snapshot OLDER than the state it judges. That last one is the only race in the whole audit that can make a DM the user has just received vanish from the app. The fixes are parameterized static SQL, exactly the style already in place and already tested on `node:sqlite`; the risk comes from touching DELETEs, so do it with the tests written first.

**Order.** After workstream 4. **Write the store tests first**: this touches `DELETE`s.

- [x] 🟡 Anti-ghost reconciliation erases a room created DURING its own network request - `db/store.ts:178` → `LIST_KNOWN_RIDS` is taken **before** `subscriptions.get`, and the purges become `rid IN (known) AND rid NOT IN (live)`. A DM born during the flight is in neither list: it is out of reach. It is the ORDER of the two reads that carries the correctness, not any delay.
- [x] 🟡 Catch-up cursors outlive the data they describe - `db/schema.ts:242` → `DELETE_ROOM_CURSORS` when leaving the room, `PURGE_MISSING_CURSORS` in the purge transaction. `scope <> '*'` protects the global cursors, whose loss would restart a full catch-up.
- [x] 🟡 The send and upload queues are never purged with their room: zombie rows replayed forever - `db/upserts.ts:246` → the purge transaction goes from three DELETEs to **seven** (outbox, uploads, drafts, cursors on top), and `deleteRoom`/`deleteBySubId` erase the same rows right away, since reconciliation only happens once per session and a zombie row cost two REST calls per connection setup until then.
- [x] 🟡 No retention: `messages` and its satellite tables never stop growing - `db/schema.ts:77` → `APPLY_RETENTION` (500 per room, `ROW_NUMBER() OVER (PARTITION BY rid)`), run once per session after catch-up. Two exemptions: optimistic messages (`updated_at = 0`, which the server will not return) and thread roots still referenced (otherwise the thread screen loses its head).
- [x] **Workstream exit**: clean `tsc`, **598 tests / 116 suites** green (against 584), clean eslint on the 8 touched files, and **the cut proven on Android's real SQLite**: 603 messages injected into the bench's `gros-general`, app relaunched, 502 on return (the 500 most recent plus the two exempted).

> **Deliberate deviation no. 1: the snapshot covers SEVEN tables with a rid, not the audit's three.** `rooms ∪ subscriptions ∪ messages` would have been enough for the anti-race, but not for recovery: an `outbox` row orphaned by a purge from BEFORE this fix no longer has its rid anywhere else, so a purge bounded to the three tables would never have reached it, and it would be replayed at every connection setup, forever. A test pins it (`an orphaned outbox (room already purged) is picked up`).

> **Deliberate deviation no. 2: retention partitions, it does not take a list of rids.** The audit proposed a `json_each` of the rids like the purges. `ROW_NUMBER() OVER (PARTITION BY rid)` does the same job in a single DELETE, over ALL rooms, including those a list built upstream would have missed. The SQL stays static and a single parameter suffices (the quota).

> **Deliberate deviation no. 3: `deleteRoom` still does not erase messages.** It now erases the four satellites, but messages remain the reconciliation's job, as before this workstream. The asymmetry is deliberate (it is outside the audit's scope) but deserves saying: `deleteRoom` alone does not make the database consistent.

> **Method note.** Store tests written BEFORE the wiring, as the order required: this touches `DELETE`s. Each fix proven BY REMOVAL: snapshot taken after the request → 1 targeted failure; the `IN (known)` bound removed from the SQL → 6 failures; the two retention exemptions removed → 2 failures, one per exemption. And an end-to-end proof on the emulator: database extracted with `run-as`, 603 messages injected (including an optimistic one, a thread root and its reply), database pushed back, app relaunched, database reread: 502, with the optimistic message and the root intact and the oldest message erased.

## 7. Upload queue: no duplicates, no silent disappearance

**🟠 high** · fix risk **medium** · effort **several-days** · 7 findings

> This is the weakest link in the repo. The TEXT path (lib/outbox.ts) has acquired, scar by scar, a client `_id`, confirmation via `chat.getMessage` and an optimistic message; the FILE path has none of that. Real consequences: a photo sent offline disappears from the screen without the slightest sign (the user sends it again and will have two), a lost `mediaConfirm` response posts the message twice with one more orphan file on the server, and a permanently failed row re-pushes all its bytes at every return to the foreground. None of these paths is covered by tests, hence the order imposed below: tests first, migration after.

**Order.** **Write the missing tests first** (status 0, queue SQL), then the banner, then the `file_id` migration.

- [x] 🟠 A file sent offline disappears from the screen without a trace - `lib/uploadQueue.ts:187` → the room banner is no longer filtered on `failed`: it shows ALL rows, with a label per status (`room.filePending`, `room.fileSending`, `room.fileNotSent`, all three in both catalogs). "Réessayer" (retry) only shows on a failure: on a row already queued, it would mean nothing.
- [x] 🟡 A lost response on `rooms.mediaConfirm` posts the same file TWICE - `lib/upload.ts:86` → `televerser` is split into `uploadBytes` / `confirmMedia`, the `fileId` is persisted BETWEEN the two (migration `0013`, nullable column), and recovery skips the bytes and then asks SQLite whether the message is already there. When the database does not know, a targeted catch-up of the room fills it in BEFORE deciding.
- [x] 🟡 No "in progress" state: "Abandonner" (discard) during a recovery deletes the row but the message gets posted anyway - `lib/uploadQueue.ts:196` → a `sending` status set by an atomic claim and excluded from the listing; `TransportUpload` exposes a switch (`onCancelable` → `task.cancelAsync()`); the discard intent is checked BEFORE the confirm (the only window where it really prevents the message from existing) and again before ingestion.
- [x] 🟡 Failed rows are replayed at every return to the foreground, with no cap or backoff - `db/upserts.ts:330` → `LIST_UPLOADS_TO_SEND` now returns only the `pending` ones. A failure is a terminus; only the "Réessayer" gesture re-arms it (`REARM_UPLOAD`). A cap, not a delay.
- [x] 🟡 `messageDelivered` confuses "the server did not answer" with "the message was not delivered" - `lib/outbox.ts:197` → three verdicts instead of two: the document, `null` if the server says no, `UNKNOWN` on a `RestError` with status 0 or 429. On `UNKNOWN` the pass stops and the row stays `pending`.
- [x] ⚪ No temporary file is ever deleted - `ui/prepareAttachment.ts:27` → `ui/temporaryFiles.ts`, injected into the engine (it cannot live in `lib/`, where `expo-file-system` does not exist). Deletes when the row is settled, on discard, when a preview is removed, when an attachment is replaced and after recompression. **The guard is the core**: nothing is deleted outside the app's cache, never a `content://` nor a file opened in place.
- [x] 🟡 The network failure path and the upload queue SQL are tested nowhere - `lib/uploadQueue.test.ts:116` → written FIRST, as the order required: `describe('upload queue')` in `db/upserts.test.ts` (11 cases, including the field-by-field read-back that guards the cast in `db/store.ts`) and 20 cases in `lib/uploadQueue.test.ts`. The fake store reproduces the SQL's semantics: a more permissive fake would let through what production fails.
- [x] **Workstream exit**: clean `tsc` ✅, green suite ✅ (634 / 119 suites, against 598 / 116), clean eslint on the 14 touched files ✅ (apart from the pre-existing error at `ui/sync.tsx:138`), `assembleRelease` ✅, **launch on the Pixel ✅ (30/07/2026, a day late: the phone was not plugged in at closing)**: the banner's three states observed in release against `chat.barrut.me`, see the method note.

> **Server fact discovered during the workstream, recorded in `CLAUDE.md`.** Replaying `rooms.mediaConfirm` on the same `fileId` is **undetermined**, and both outcomes are bad: immediate replay → a SECOND message is posted but the response is **200 with the FIRST message** (hence indistinguishable from a success); delayed replay → **`[invalid-file]`**, a flat refusal that shows "non envoyé" (not sent) on a file that was in fact delivered. Both were observed on the 8.5 bench. No server response is therefore usable: deduplication is entirely local, and the client must make sure its database KNOWS before deciding.

> **Deliberate deviation no. 1: the local safeguard was not enough on its own.** The audit prescribes "ask SQLite, not the network". Right, but insufficient in the very case it targets: on restart after a kill, no room screen is mounted, `stream-room-messages` is subscribed to nothing, and the `messages` table does not know the message of the lost confirm. ## 8. DDP and REST transport: do not kill a healthy socket, do not sleep without listening

**🟡 medium** · fix risk **medium** · effort **day** · 6 findings

> The domain is solid and well tested, but four precise defects make the app punish itself on a degraded network: a liveness probe sent too early closes a working socket (server behaviour verified on the bench), the reconnection driver keeps reopening sockets in the background against the documented intent, a 429 retry sleep ignores cancellation and makes concurrent calls converge, and `/api/info` alone escapes the whole of the module's defences, to the point of being able to block the login screen for good. Each fix is local to a module already covered by tests.

**Order.** Independent. To be handled in one block so as to pay for only one reconnection test campaign.

- [x] 🟡 The liveness probe sent during the DDP handshake kills a healthy socket 10 s later - `lib/ddp.ts:437` → state guard at the top of `checkAlive()`: probe only in `connected` or `authenticated`, since a handshake already has its own timeout. And `receive()` now handles `msg: 'error'`, rejecting the wait named by `offendingMessage.id`: that silence was the cause of the damage, not the probe itself.
- [x] 🟡 The reconnection driver is not suspended when going to the background - `ui/sync.tsx:389` → `Reconnector.suspend()` / `resume()`, a reversible flag (distinct from `stop()`, which is final) that closes BOTH paths: the timer already armed, disarmed on the spot, and the restart that the failure or the recording of an in-flight attempt would request next. > **Deliberate deviation no. 1: `resume()` resets the backoff to zero.** The audit only asked for a reversible flag. ## 9. Dead session and logout: back to login, and take everything on the way out

**🟠 high** · fix risk **HIGH** · effort **day** · 5 findings

> Three holes converge on the same symptom: the app stays in a state it believes valid and the user has no way out. I place it AFTER the low-risk workstreams because triggering an automatic logout is the most dangerous fix in the whole audit: a discrimination error ejects the user wrongly. To be done with its predicate test written first.

**Order.** **Write the `isTokenRejected` predicate and its four-case test BEFORE wiring it.** Do the per-account E2EE key part first, which is risk-free.

> **The fact that decides everything, probed on the 8.5.1 bench BEFORE writing a line (30/07/2026).** The whole safety of the workstream rests on one question: *can a 401 arrive while the session is healthy?* On 8.5, **no: 401 means "not authenticated", and nothing else**:
>
> | situation | response |
> |---|---|
> | token revoked by `logout`, bogus token, missing token, bogus uid | **401** `{"success":false,"error":"You must be logged in to do this.","status":"error"}` |
> | missing permission (admin route) | **403** `User does not have the permissions required for this action [error-unauthorized]` |
> | kicked from the room (measured: alice added then `groups.kick`) | **400** `error-not-allowed` / `error-room-not-found` |
> | 2FA required on a sensitive operation | **400** `totp-required` |
> | **wrong 2FA code** | **400** `totp-invalid` |
>
> The last line closed the only truly worrying scenario the refutation raised: a typo in "Mon profil" (my profile) would have destroyed the session **and** the E2EE key if `totp-invalid` had been 401. It is 400.
>
> The only exception, and it produced a test: **`/api/v1/login` maps ALL its failures to 401** with a perfect Rocket.Chat envelope: bogus resume token, empty body, nonexistent user, wrong password all return `{"success":false,"error":"Unauthorized","status":"error"}`, indistinguishable. It is the hook's `anonymous` guard that sets it aside: without it, **a mistyped password would destroy the current session**.

> **Hole found in the fix itself, by adversarial refutation.** Two, in fact, both real and fixed:
>
> 1. **`understoodResponse` lied.** The field claims to certify the Rocket.Chat envelope; the code hard-coded `true` as soon as the body parsed as JSON. An API gateway answering `401 {"message":"Unauthorized"}` (and the target server is behind a reverse proxy) therefore passed the predicate and got the E2EE private key of a valid session erased. The check now looks for a mark of the envelope (`success`, `status`, `errorType`). Proof by removal: neutralizing the line kills a test.
> 2. **The purge of the legacy E2EE key only saw the ACTIVE server.** Yet `SyncProvider` only mounts on an open session: a user who had unlocked E2E on a server and then left it kept their **decrypted** RSA JWK under a key no code derives any more; "unreachable" would have meant *indestructible*. The sweep now goes through `listKnownServers()`, at `SessionProvider` startup, outside any session.

> **Deliberate deviation no. 1: the SQLite database is NOT deleted on logout**, contrary to what `docs/AUDIT.md` gave as its preference. The audit explicitly allowed deciding otherwise provided it was documented; here is why. Deleting it live breaks the app in three verified ways: (a) `db/migrate.ts` memoizes the migration promise by file name and clears it **only on failure**: after deletion and then reconnection of the same account in the same process, `migrate()` does not run and the new database has **no tables**, deterministically and with no race at all; (b) nothing allows waiting for writes to quiesce (`db/writeQueue.ts` exposes neither stop nor drain, the upload queue receives no `isDiscarded`); (c) `logOut` can run 30 s after the `setState({ phase: 'disconnected' })` (three REST calls with a 15 s timeout) while the user has already logged back in: the deletion would land on the **live** database, and `db/client.ts` already forbids that move in black and white. Chosen instead: masking the E2E plaintext through the write queue, which is ordered with everything in flight and closes nothing. The offline cache therefore survives a logout, which is also what makes coming back instant.
>
> **Limit recorded with it.** `hideEncryptedMessages` is an `UPDATE`: it makes the plaintext invisible to SQL, it does not overwrite the freed bytes in the file. For "mask" to mean "erase from disk", `PRAGMA secure_delete = ON` would be needed at open time, a decision that touches the write profile of the whole app, so not one to take in passing in this workstream. To be decided on its own.

> **Deliberate deviation no. 2: no allowlist on the `login` error text.** The synthesis proposed turning off the session, on that path, only if `error === 'Unauthorized'`, to spare a temporarily blocked account (`error-login-blocked-for-user`, which the server bundle does pass through as is). Measured: on the bench, **all** 401s from `/login` carry `Unauthorized`, and account blocking is unreachable: the rate limiter returns 429 first (and a 429 is not a 401, so it triggers nothing). The allowlist would therefore have changed nothing observable, but it would have made revocation depend on a **server text string**: the day Rocket.Chat rewords it, the zombie state silently returns. The false positive avoided is minor and reversible (log in again once unblocked); the risky regression is not.

> **Deliberate deviation no. 3: no second logout path around the `Reconnector`**, which the audit prescribed in part (2) of its fix. The hook makes it redundant: a 401 from `catchUpGlobal` bubbles up `onTokenRejected` → `revoke` → `setState({ phase: 'disconnected' })` → the `SyncProvider` effect reruns → `reconnector.stop()`. The deliberately blind `catch` in `lib/reconnect.ts` has nothing left to decide, and writing it would add a second discrimination site, hence a second false-positive risk: the only real danger of this workstream.

> **Method note.** Proof by removal on the five load-bearing lines, each one killing the expected tests: the predicate's `TwoFactorError` guard → 1; `understoodResponse` condition → 1; envelope check → 1; anonymous call guard → 1; capturing the token BEFORE the request → 1. The `TwoFactorError` guard was at first **decorative**: `TwoFactorError` lacking `understoodResponse`, removing it broke nothing. The 2FA challenge does carry a Rocket.Chat envelope, though; it was given one, and the guard became load-bearing. A trap met once more: my first removal of the envelope check targeted a multi-line pattern that `perl` did not match, and the suite stayed green **without anything having been removed**. A removal that does not change the file is an empty test; always check that the substitution bit before reading the verdict.

## Do not touch

Flagged during the audit, then dismissed. These lines are here so they do not get rediscovered in six months.

- **The double read in `setUpConnection`** (lib/connectionSetup.ts:89 and 104, two `catchUpAll` per connection setup). The finding is real (2 x rooms.get + 2 x subscriptions.get at every return to the foreground, on a route limited to 10 req/min) but the second read is WHAT guarantees that no document falls between the read and the arming of the subscriptions. Making it conditional touches the core of connection setup, with no non-regression test today. To revisit only after the "deduplicated catch-up" workstream (which already removes most of the waste) AND once lib/connectionSetup.test.ts is extended.

- **Decoupling the `SyncProvider` effect from the `state` object (key `baseUrl|userId|authToken` as a dependency).** Proposed by two reviewers, contradicted by a third after checking: `RcTranslator` and `OutboxEngine` capture `session.username` at construction (providers/rocketchat/index.ts:40), so freezing the key breaks the display name and the DMs' `dmOtherUsername` after a rename. The real fix (memoizing the write queue with the connection) removes the danger without touching the dependencies; rebuilding the engine for nothing on a rename then becomes mere waste, to be handled later with a translator that rereads its username.

- **The 24 eslint react-hooks/immutability and refs errors in ui/imageViewer.tsx and ui/audioPlayer.tsx.** Checked: they are `SharedValue` writes in gesture worklets, that is Reanimated's normal API, which the rule (React Compiler model) does not model. `flatten` does carry its `'worklet'` directive. The only contentious case, `me.current.pause = …` written during render, is benign (the coordinator compares the object's identity, never the closure). Touching it would only add indirections.

- **The "inverted list + maintainVisibleContentPosition turned off" idiom and the smoothing of incoming messages in app/room/[rid].tsx** (comment l.74-99), as well as the secondary sort key `desc(messages.id)`. These are measured scars, not oddities; splitting the file must touch neither the list engine nor these settings.

- **The `setTimeout` in ui/launchPicker.ts.** It is the only fixed delay in the repo that is explicitly argued (Android view tree NPE when launching a picker, three successive fixes: c9e6694, e06f658, ad8ecec). The "no waiting as a fix" rule targets data synchronization, not documented workarounds for platform bugs.

- **`closeDatabase` (db/client.ts:45): do NOT call it in the `SyncProvider` cleanup.** The connection is shared and the cleanup runs while writes from the old engine may still be in flight; closing it under them is worse than leaving the connection open. The right move is to document the choice in db/client.ts and to filter `databaseName` in ui/liveQuery.ts (finding kept), not to call the function.

- **The WebView exception in app/call/[callId].tsx.** The native Jitsi SDK targets RN ~0.79 and ships react-native-webrtc: the exception is justified and must stay. What is needed is to record it in ROADMAP §4.2 and bound it to one origin, not to call it into question.

- **`Push_request_content_from_server` (content-less push, `push.get` on reception).** It is a dated user decision (2026-07-16: nothing at Google/Apple). Every push finding must live with it, never propose lifting it.

- **Do not pass a client `_id` to `rooms.mediaConfirm` to deduplicate uploads**: the server schema is `additionalProperties: false`. Deduplication must go through persisting the `fileId` client-side, as chosen in the uploads workstream.

- **Do not remove the long press from app/room/[rid].tsx:584 and app/thread/[id].tsx:245 to fix the empty action sheet**: it would be the same rule duplicated in two screens, and it would remove the haptic feedback confirming that the press registered. The fallback is done in app/message-actions.tsx.
