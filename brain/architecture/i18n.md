# Internationalisation

Both apps ship French and English only, with no i18n library: each has one in-code catalog, `{name}` interpolation and a `singular | plural` form. The mobile catalog is `apps/mobile/ui/messages.ts`; the desktop catalog is `rv-core/src/i18n.rs`, shared by the GTK app and, through rv-ffi, the SwiftUI app. Desktop strings reuse the mobile wording, but the two catalogs are separate files with different keys.

## Shared conventions

- Languages: `fr` and `en`. The preference is `auto` (follow the device), `fr` or `en`.
- Keys are namespaced by screen or component (`login.*`, `room.*`, `settings.*` on mobile; `login.*`, `room.*` on desktop), with `sys.*` for Rocket.Chat system messages in both.
- `{param}` placeholders; a template containing ` | ` is split into singular and plural, chosen by the numeric `n`. French puts 0 and 1 in the singular, English only 1.
- Language names in the picker are endonyms ("Français", "English"), identical in both languages; only "Automatic" is translated.
- Server-sent i18n keys for slash commands (`Slash_Shrug_Description`...) have their own small table in each app (`lib/commands.ts`, `rv-core/src/commands.rs`); an unknown key that looks like one is shown with underscores turned into spaces.

## Mobile

### The catalog (`ui/messages.ts`)

A pure module (loadable under Node). `fr` is the reference object: its keys define the type `TranslationKey`. `en` is typed `Record<TranslationKey, string>`, so `npx tsc --noEmit` rejects any missing or extra English key. `CATALOGUES = { fr, en }`; `Language` and `LANGUAGES` derive from it. Also here:

- `translate(language, key, params)`: picks the template (falling back to French if a key were somehow missing), resolves the plural, substitutes `{param}`. A placeholder with no value is left as `{param}` so the omission is visible.
- `deviceLanguage()`: the device language read in pure JS through `Intl.DateTimeFormat().resolvedOptions().locale` (Hermes ships ICU). `fr*` gives `fr`, anything else `en`. No native module, so no dev-client rebuild and no dependency to justify against `ROADMAP.md` §4.2.
- `timeFormatter(language)` and `dayFormatter(language)`: message time and day-separator labels, tied to the chosen language rather than the device locale (FR "14:05", EN "2:05 PM"; "Today"/"Yesterday" from the catalog, then a date with weekday in the current year, with year otherwise). Factories meant to be memoized, since building an `Intl.DateTimeFormat` is costly.
- `ui/messages.test.ts` checks interpolation, both plural rules, that both catalogs have exactly the same keys, that no value is empty, and the formatters.

### The store (`ui/i18n.ts`)

The only platform part: persistence in expo-secure-store under the key `preferred-language`, global to the device (not per server). It is read synchronously when the module loads (`readMovedKeySync` over `SecureStore.getItem`, `STORED_KEYS.preferredLanguage` in `lib/storageKeys.ts`, which moves a value still under the pre-0016 name `langue-preferee` on first read), so the first render already has the right language; any unexpected value or read error means `auto`. The active language is a module-level store, not a provider (same pattern as `ui/identityStore.ts`, see [mobile-app.md](mobile-app.md)), so switching language re-renders only subscribed components. API:

- `useT()`: the bound translator, stable until the language changes. `useLanguage()`, `useLanguagePreference()`, `useTimeFormatter()`, `useDayFormatter()`.
- `setLanguage(pref)`: switches immediately; `auto` deletes the key, an explicit language writes it with `AFTER_FIRST_UNLOCK` so the iOS NotificationService extension can read it on a locked phone.
- `translateCurrent(key, params)`: for code outside components (native handlers, module callbacks, `ui/sync.tsx` errors). Prefer it to `translate(deviceLanguage(), ...)`, which would ignore an explicit choice.

Pure `lib/` modules that need sentences take the translator by injection (for example `lib/systemMessages.ts` maps system message types to `sys.*` keys and receives `t`).

Known boundary: raw error messages thrown inside `lib/`, `ui/` and the transport (for example "server unreachable") are English and not translated. `lib/` stays pure and platform-free, and these only surface through `e.message` as a last resort.

### Native strings outside the JS catalog

Notifications built while the JS runtime may be dead cannot use `ui/messages.ts`:

- Android: `NATIVE_STRINGS` in `plugins/with-fcm-deeplink.js` (encrypted message, "You", new message, reply, reply not sent) is written at prebuild to `res/values/strings.xml` (English default) and `res/values-fr/strings.xml`. The Kotlin service reads `key_v1-preferred-language` (else the old `key_v1-langue-preferee`) from expo-secure-store's SharedPreferences, decrypts it, and applies that locale before the phone's.
- iOS: the `LocalizedStrings` enum in `plugins/ios-notification-service/NotificationService.swift` and inline strings in `modules/notification-reply/ios/NotificationReplyAppDelegate.swift`, both choosing by `preferredLanguage()` from `SessionPush.swift` (keychain `preferred-language`, else the old `langue-preferee`, else `Locale.preferredLanguages`).

### Adding a mobile string

1. Add the key and French text to `fr` in `ui/messages.ts`, in the right namespace.
2. Add the same key to `en`. `npx tsc --noEmit` fails until you do.
3. Use `const t = useT(); t('room.someKey', { n })` in a component, or `translateCurrent` outside one.
4. For a native notification string, edit `NATIVE_STRINGS` (Android) or the Swift strings (iOS). Those need a prebuild and a dev-client rebuild ([mobile-native.md](mobile-native.md)); JS catalog changes only need a Metro reload.

Adding a language means adding a catalog to `CATALOGUES` and handling it in `deviceLanguage`, `isPlural`, the formatters and the stored-value check in `ui/i18n.ts`, which currently only accept `fr` and `en`.

## Desktop

### The catalog (`crates/rv-core/src/i18n.rs`)

One static `CATALOG: &[(key, French, English)]`. The active language is a process-wide `AtomicU8` behind `current()` and `set(Lang)`; it defaults to English until a UI calls `set`. Functions:

- `t(key) -> &'static str`. A missing key triggers `debug_assert!` (a panic in debug builds and tests) and shows `?` in release.
- `tf(key, &[(name, value)])` substitutes `{name}`.
- `tn(key, n)` picks the plural form and fills `{n}`.
- `system_message(kind, param)` maps a Rocket.Chat `t` type to its sentence (said after the author's name); unknown types fall back to `sys.unknown` / `sys.unknown_param`.

Tests in the same file check that keys are unique, both languages are non-empty, French and English have the same number of `{` placeholders, plus the plural rules and system messages. rv-core uses the language itself too, for example to word slash-command descriptions (`session.rs` passes `i18n::current()` to `commands::parse_list`).

### GTK (`crates/rv-gtk/src/i18n.rs`)

Re-exports rv-core's functions and adds the choice: a plain file `language` in GLib's user config dir under `rocket-vibe-rs/` (so `~/.config/rocket-vibe-rs/language` on Linux) containing `auto`, `fr` or `en`. `init()` (called from `main.rs` at startup) applies it; `auto` follows `glib::language_names()`. `locale()` maps the language to a `chrono::Locale` for localized dates (`rows.rs`). The settings dialog (`settings.rs`) writes the file through `save_choice` and says the change "takes effect on next launch": nothing re-renders live.

### SwiftUI (`apps/desktop/macos/Sources/RocketVibeKit/Strings.swift`)

The macOS app reads the same rv-core catalog through rv-ffi exports (`set_french`, `t`, `tf`, `tn`, `system_message` in `crates/rv-ffi/src/lib.rs`). `Strings.setUp(configDir:)`, called by `AppModel`, reads `<configDir>/language`; `configDir` comes from rv-ffi's `Dirs::glib`, the same XDG-style `rocket-vibe-rs` directory the GTK app uses, so the saved choice is shared between the two desktop apps. `L(key)`, `L(key, args)` and `L(key, count:)` wrap `t`, `tf` and `tn`. `SettingsView.swift` writes the file and also shows the restart notice. See [desktop-macos.md](desktop-macos.md).

### Adding a desktop string

1. Add `("area.name", "Français", "English")` to `CATALOG` in `crates/rv-core/src/i18n.rs`, with the same placeholders in both.
2. GTK: `use crate::i18n::{t, tf};` then `t("area.name")`. SwiftUI: `L("area.name")`. No binding regeneration is needed for a new key, since keys are plain strings across the FFI.
3. `apps/desktop/scripts/build.sh` runs the tests in the build container; the uniqueness and placeholder test catches mistakes.

## Parity

Same two languages, same `auto | fr | en` choice and plural rules in both apps. Differences: mobile switches language live, desktop needs a restart; mobile keys its catalog by the `fr` object's keys with compile-time completeness, desktop by a tuple table checked by unit tests; mobile stores the choice in the secure store, desktop in a plain config file.
