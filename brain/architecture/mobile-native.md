# Mobile native layer

The mobile app uses Expo's Continuous Native Generation: `android/` and `ios/` are build artefacts, regenerated by `expo prebuild`, and every native customisation lives in a config plugin (`apps/mobile/plugins/`), a local Expo module (`apps/mobile/modules/`) or a patch-package patch (`apps/mobile/patches/`). This doc lists each one, explains the Metro crypto aliasing, says when a dev-client rebuild is needed, and gives the iOS status.

## CNG: nothing native is committed

`apps/mobile/.gitignore` ignores `/android/` and `/ios/` (and `modules/*/android/build/`). In SDK 57 `expo prebuild` wipes and regenerates by default, so a hand edit inside `android/` is silently lost at the next prebuild. This has happened: an ABI tweak made by hand in `gradle.properties` vanished and the APK grew from 60 to 150 MB, which is why `with-target-architectures.js` exists. `npm run prebuild` runs `expo prebuild --platform android --clean`; builds are local Gradle, never EAS (see [../operations.md](../operations.md)).

`app.json` lists the plugins applied at prebuild: Expo's own (`expo-router`, `expo-secure-store`, `expo-sqlite`, `expo-notifications` with icon, colour and `default` channel, `expo-audio`, `expo-font` with the Baloo 2 and Nunito files, `expo-video`, `expo-image-picker` with permission texts, `expo-share-intent` with Android intent filters and iOS activation rules, `expo-sharing`) and the five local ones below. Android permissions declared there: `CAMERA`, `RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS`. `googleServicesFile` points at `google-services.json` (Android) and `GoogleService-Info.plist` (iOS), both gitignored secrets.

## Config plugins (`apps/mobile/plugins/`)

Each plugin that rewrites a generated file is idempotent (it checks for a marker before editing) and throws if its anchor is missing, so a template change fails the prebuild instead of silently skipping. Their pure functions are exported (`internals`, `neutralize`, `sign`) and tested by `plugins/*.test.mjs`, which `npm test` runs.

| Plugin | What it does |
|---|---|
| `with-fcm-deeplink.js` | The Android push path. Generates `RocketVibeMessagingService.kt` (an `ExpoFirebaseMessagingService` subclass registered above expo's priority) that strips the FCM `notification` block so the message becomes data-only and reaches the app even when killed. Rocket.Chat message pushes are posted as one `MessagingStyle` notification per room (id derived from the rid) whose tap opens `rocketvibe://room/<rid>?host=<server>`; other pushes fall through to expo-notifications. In hidden-content mode it reads the session from expo-secure-store's SharedPreferences (decrypting via the AndroidKeyStore, no JS runtime) and calls `push.get`; on failure it shows "New message" and schedules `PushCatchUpWorker` (WorkManager: network constraint, 30 s linear backoff, 8 attempts, unique per messageId) except on 401/403. It also generates `NotificationReplyReceiver`, a `BroadcastReceiver` for the inline "Reply" action (RemoteInput key `rv_reply`) that posts via `chat.sendMessage`. Already-shown messageIds are remembered in the SharedPreferences `rvpush-shown` (the previous build's `rvpush-affiches` is still read); catch-up work names are `push-catch-up-<messageId>`. The pre-rename names stay for one release so notifications and WorkManager jobs posted by the previous build still land: `ReponseNotifReceiver` and `RattrapagePushWorker` are generated as empty subclasses of the new classes (the old receiver is also declared in the manifest), the old RemoteInput key `rv_reponse` is still read, and cancelling a catch-up cancels both `push-catch-up-` and `rattrapage-push-` names. Adds `firebase-messaging` and `androidx.work` Gradle dependencies, manifest entries, and the user-visible strings in `res/values` (English) and `res/values-fr`. Writes a diagnostic log to `files/rvpush.log` (ids only, no content); the debug probe is armed by the flag file `files/rvpush-probe`. |
| `with-ios-push.js` | The iOS push path: `FirebaseAppDelegateProxyEnabled = false` (no swizzling against expo-notifications), Firebase pods with `modular_headers` in the Podfile, a keychain access group shared by app and extension (first in the app's list, since that is where expo-secure-store writes), and a `NotificationService` app-extension target (iOS 16.4 minimum) built from `ios-notification-service/NotificationService.swift` plus `modules/notification-reply/ios/SessionPush.swift`. |
| `ios-notification-service/NotificationService.swift` | Not a plugin but its payload: the Notification Service Extension. Reads the session from the shared keychain, fetches `push.get`, rewrites title and body, sets `threadIdentifier` to the rid and stores `ejson` in `userInfo["body"]` for expo-notifications' tap routing. No WorkManager equivalent: a failed fetch stays "New message". |
| `with-target-architectures.js` | Sets `reactNativeArchitectures=arm64-v8a,x86_64` in `gradle.properties` (Pixel and Apple Silicon AVD are arm64, the Linux AVD is x86_64); drops about 55 MB of unused ABIs. CI overrides it to `arm64-v8a` on the Gradle command line. |
| `with-signature-release.js` | Adds a `release` signing config fed by `RV_KEYSTORE`, `RV_KEYSTORE_PASSWORD`, `RV_KEY_ALIAS`, `RV_KEY_PASSWORD`, switches the release build type to it, and adds a task-graph guard that fails any Release task when `RV_KEYSTORE` is empty, rather than silently signing with the debug key (Android refuses an update signed by another key). |
| `with-incoming-share.js` | Patches `MainActivity.onCreate`: when the activity is restored (`savedInstanceState`) or launched from history with a `SEND`/`SEND_MULTIPLE` intent, it swaps in the launcher `MAIN` intent, so a share is not replayed on every relaunch. |

Push details are in [../features/notifications.md](../features/notifications.md) and `docs/PUSH.md`.

## Local Expo modules (`apps/mobile/modules/`)

Autolinked by Expo from `modules/`. Each `index.ts` uses `requireOptionalNativeModule`, so the module is `null` on a platform that lacks it and callers branch on that. These files are importable only inside the app: expo-modules-core does not load under Node, so decision logic stays in pure modules (for example `ui/attachmentQuality.ts`).

| Module | Platforms | Purpose |
|---|---|---|
| `video-compressor` | Android (Kotlin, Media3 Transformer), iOS (Swift, AVFoundation) | `compress(uri, maxShortSide, videoBitrate)`: re-encodes a video to MP4 H.264 before upload, short side capped, writing into the app cache so `deleteIfTemporary` can clean it. Used by `ui/prepareAttachment.ts`; if the result is not smaller, the original is sent. |
| `downloads` | Android only | `save(source, name, type)`: copies a cached file into the public Downloads folder (`MediaStore.Downloads` from Android 10, the public directory before). On iOS it is `null` and `ui/attachment.ts` opens the share sheet instead. |
| `fcm-token` | iOS only | Hands the APNs token to Firebase and returns the FCM token Rocket.Chat expects as `gcm`; emits `tokenRefreshed` on rotation. Android gets its FCM token directly from `getDevicePushTokenAsync()` (`lib/push.ts`). |
| `notification-reply` | iOS only, no JS API | `NotificationReplyAppDelegate`, an `ExpoAppDelegateSubscriber` registered at launch (so it is in place when iOS wakes the app only to deliver a reply), posts the notification's "Reply" text via `chat.sendMessage` natively. `SessionPush.swift` reads session and language from the keychain and is compiled into both this pod and the NotificationService extension. |

## Patches (`apps/mobile/patches/`)

`npm install` runs `patch-package` (`postinstall`). One patch, `expo-share-intent+8.0.1.patch`, on the library's Android Kotlin:

- tolerates a `ContentProvider` returning an empty cursor or no `DISPLAY_NAME`/`SIZE` (the original crashed the whole app on share with `CursorIndexOutOfBoundsException`), falling back to the URI's last segment and `application/octet-stream`;
- clears the pending intent before handling it, so an exception cannot leave a share pending forever;
- keeps a share received through `onNewIntent` while React is not ready, instead of dropping it, and stops `OnNewIntent` from replaying a buffered intent.

A patch to a native file only takes effect after a prebuild and rebuild.

## Crypto: Metro aliases `crypto` to react-native-quick-crypto

`lib/e2e/crypto.ts` imports from `crypto` and `buffer` as if under Node. `metro.config.js` overrides `resolveRequest`: in the app bundle `crypto` resolves to `react-native-quick-crypto` (a Nitro native module exposing the `node:crypto` API over OpenSSL) and `buffer` to `@craftzdog/react-native-buffer`. Under Node tests no alias applies, so the same code runs on real `node:crypto`. Footgun: `buffer` must point at the leaf implementation, not quick-crypto's barrel, which itself imports `buffer`; aliasing to the barrel creates a cycle and a half-initialised module (`Cannot read property 'Certificate'`). The same file also adds `sql` to `sourceExts` for Drizzle migrations ([mobile-data.md](mobile-data.md)). E2EE itself is in [e2ee.md](e2ee.md).

## When a dev-client rebuild is needed

`npm start` runs `expo start --dev-client`: Metro serves JS into an installed development build. A Metro reload covers any change to TypeScript under `app/`, `ui/`, `lib/`, `db/`, `providers/` and to the JS side of `modules/*/index.ts`. A new native build (`npm run prebuild` then `npm run android` or Gradle) is required after:

- adding, removing or upgrading a dependency with native code (for example quick-crypto, any Expo module);
- editing a config plugin, its embedded Kotlin or Swift, or the native parts of `app.json` (plugins list, permissions, package, icons);
- editing Kotlin or Swift under `modules/`;
- changing a patch that touches native files.

This is why some choices avoided a native dependency: drafts live in SQLite instead of MMKV, and the device language is read through `Intl` (see [i18n.md](i18n.md)).

## iOS status

Prepared, never built. `app.json` has an `ios` section (`bundleIdentifier` `com.rocketvibe.app`, permission strings), `ui/theme.ts` picks PostScript font names on iOS, and the iOS halves of `video-compressor`, `fcm-token`, `notification-reply` and the NotificationService extension exist. `docs/DEV.md` and `docs/PUSH.md` state that everything was verified only from Linux (`expo prebuild --platform ios --no-install`, `swiftc -parse`, the JS bundle via `expo export --platform ios`) and that the app has never been compiled with Xcode. The CI workflow (`.github/workflows/mobile.yml`) builds Android only. Building needs a Mac: `npx expo prebuild --platform ios`, then Xcode with three targets (`rocketvibe`, `NotificationService`, `ShareExtension`).
