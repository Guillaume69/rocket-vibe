# Shared crates: protocol, client, crypto

The Rust crates in `crates/` are shared by the Vibez server and the three client apps. They carry the native protocol (the Vibez server's own wire contract, not Rocket.Chat's), the HTTP client the desktop uses to speak it, and the MLS end-to-end encryption engine with its bridges to Android and the browser. Read [overview.md](overview.md) for where they sit, [server.md](server.md) for their main consumer, and the `e2ee-*` feature pages for what the encryption does for users.

## Workspaces and locks

The root `Cargo.toml` is a resolver-3 workspace of `apps/server`, `crates/rv-protocol`, `crates/rv-client`, `crates/rv-crypto-public` and `crates/rv-link-preview`. Everything else keeps a workspace of its own, on purpose:

| Workspace | Why it stands apart |
|---|---|
| root | The server and the public crates it needs; the server never links the private vault. |
| `apps/desktop` | The desktop app ([desktop-app.md](desktop-app.md)); reaches the shared crates by path (`../../../../crates/...`), so its build container mounts the whole repository. |
| `apps/desktop/voice` | The voice sidecar, the only binary linking libwebrtc: kept out of the desktop's `cargo build --workspace`. |
| `crates/rv-crypto` | The private engine and its vault; its tests use their own `curve25519-dalek` optimisation profile. |
| `crates/rv-crypto-mobile` | A `cdylib` for Android, built per ABI by the mobile build. |
| `crates/rv-crypto-web` | The wasm build, with its own release profile (`opt-level = "s"`, LTO, `panic = "abort"`). |
| `crates/rv-voice-mobile` | A small JNI `cdylib` for Android, built apart like `rv-crypto-mobile`. |
| `crates/rv-signal` | WhatsApp's Signal protocol, written clean room; checked by its own CI job (`rv-signal.yml`). |
| `crates/rv-whatsapp` | The vendored WhatsApp engine (whatsapp-rust), a workspace of its own as upstream laid it out; checked by `rv-whatsapp.yml`. |
| `crates/rv-provider`, `crates/rv-slack`, `crates/rv-teams` | The desktop's provider clients, below rv-core; one workspace each, checked by `providers.yml` (fmt, clippy, tests), and by the desktop's own build through rv-core. |

Twelve workspaces mean twelve `Cargo.lock`. Within one semver-compatible line (`1.x`, `0.29.x`) a crate must resolve to the same version in all of them, so a fix to a shared dependency (crypto, TLS, tokio) reaches every app: `node scripts/cargo-locks.mjs` checks it (CI `cargo-locks.yml`), and `--sync` raises every lagging lock to the newest version already in use ([operations.md](../operations.md), [decisions.md](../decisions.md)).

## `rv-protocol`: the wire contract

The native v1 types, with no UI, database or Rocket.Chat dependency (`VERSION = 1`, `crates/rv-protocol/src/lib.rs`). Modules follow the server's areas: `admin`, `bots`, `cards`, `commands`, `custom_emojis`, `e2ee` (the MLS transfer objects), `emojis`, `link_previews`, `live`, `markdown`, `parity`, `profiles`, `push`, `search`, `system`, `voice`, `workflows`.

- **Capabilities.** `Capabilities` is what discovery announces; every field added after v1 is `#[serde(default)]`, so an older v1 server reads as "not supported".
- **Shared rendering.** `markdown::parse` and `mention_names` are the bounded renderer both the server and the clients use; `emojis::canonical` reads `data/emoji-aliases.json`, generated by `scripts/generate-native-emojis.mjs` from the desktop emoji table.
- **One schema, three generated copies, all committed.** `cargo run -p rv-protocol --bin export-schema` writes `docs/protocol/v1.schema.json`. `scripts/generate-native-protocol.mjs` turns it into `apps/mobile/providers/vibez/protocol.generated.ts` (types and a `nativeSchema` validator). `apps/web/scripts/sync-crypto.mjs` copies that into `apps/web/src/crypto/schema.generated.ts`. A second binary, `export-rendering-fixture`, writes `docs/protocol/native-rendering.fixture.json`.
- **Drift is a CI failure.** `apps/server/scripts/check.sh` diffs the exported schema against the committed one and runs `generate-native-protocol.mjs --check` and `generate-native-emojis.mjs --check`. Change a type, then regenerate both before committing.
- Tests: `tests/contract.rs` against `docs/protocol/v1.fixture.json`, plus `cards`, `link_previews`, `native_rendering`.

## `rv-client`: the HTTP client

`NativeClient` (`crates/rv-client/src/lib.rs`): one async method per server route (discovery, login and factors, email, push, voice, the `crypto_*` E2EE routes, about 170 in all). It takes an `http(s)` base URL with no user info, query or fragment, uses a 15 s timeout and no redirects, keeps the bearer token behind a mutex, and honours `Retry-After` per route (clamped to 1..300 s). No GTK, SQLite or keychain: the desktop's `rv-core::native` builds its session on it, and `rv-crypto`'s `native-http` feature drives the encrypted delivery worker with it. Tests run against a local listener (`src/crypto_tests.rs`) and through the server's integration tests, which use it as their client.

## `rv-crypto-public`: what the server can verify

The public halves of the encryption: account roots and device certificates (`Root`, `Device`, `Certificate`, `Revocation`), the group plans and transitions (at most 128 members and 256 devices), and the formats of archives, history shares, history backups, messages and recovery (`crates/rv-crypto-public/src/`). Everything is signed over `signing_bytes(domain, value)`, the domain, a NUL and the JSON, capped at 4096 bytes (`WIRE_LIMIT`). No private key, storage or trust decision lives here: the server uses it to refuse malformed or unsigned material without ever seeing a secret. Committed vectors in `fixtures/` are re-verified independently by `scripts/verify-*-vector.mjs` with Node and OpenSSL, in `check.sh` and in the Linux crypto job.

## `rv-crypto`: the engine

The client side of Vibez's MLS encryption (`crates/rv-crypto/src/lib.rs`): accounts and devices (`identity`, `account`, `installation`), key packages, groups and their messages (`groups`, `packages`), archives, files, history shares and backups, and the vault that holds all of it. It uses OpenMLS 0.9.0 with its RustCrypto provider, XChaCha20-Poly1305 and Ed25519, all pinned exactly; it invents no primitive.

- **The vault.** One encrypted SQLite row per account (WAL, `synchronous=FULL`, a 16 MiB document cap), sealed with XChaCha20-Poly1305 under a key held by the OS keychain (`keyring`, service `me.barrut.RocketVibe.crypto.v1`). Every transaction returns a checkpoint `(revision, SHA-256 of the sealed row)` that the caller must store in the keychain before using the result; opening refuses a database older than its checkpoint, so restoring an old copy of the file is detected. Only a crash between commit and keychain write is recoverable (`recover_committed`, one revision ahead). `protected::Manager` wraps the cycle with an OS lock; a concurrent opener gets `crypto_storage_busy`. The storage key is renewed every 30 days ([e2ee-storage-keys](../features/e2ee-storage-keys.md)). Model and invariants: `crates/rv-crypto/README.md`.
- **Features and targets.** `system-keystore` adds the OS keychain; `native-http` adds `rv-client` and tokio for the delivery worker. On `wasm32` the vault is a virtual SQLite snapshot sealed by the page with a non-extractable WebCrypto key under a Web Lock (`src/browser.rs`). On Android, file locking goes through `rustix`'s `flock`, since the standard library's is missing there.
- **Design notes** sit next to the code: `IDENTITY.md` (roots, certificates, revocations), `ENROLLMENT.md` (a new device proves possession, approval bound to the exact request), `MESSAGES.md`, `SETTLEMENT.md` (cancel or resume a send without a second POST), `RECOVERY.md` (root backup under a 32-byte recovery code), `JOURNAL.md`, `GROUP_COMMITS.md`, `GROUP_HTTP.md`, `GROUP_SETTLEMENT.md`, `PACKAGES.md`, `READMISSION.md`. The protocol specs are `docs/protocol/E2EE_*.md` and the plan is `docs/rfcs/0002-e2ee-native.md`.
- **What users get**: [e2ee-history](../features/e2ee-history.md), [e2ee-delegation](../features/e2ee-delegation.md), [e2ee-private-files](../features/e2ee-private-files.md), [e2ee-private-actions](../features/e2ee-private-actions.md), [e2ee-storage-keys](../features/e2ee-storage-keys.md). Rocket.Chat's own E2EE is a different scheme, in [e2ee.md](e2ee.md).
- Tests: inline `tests.rs` modules and the `protected_smoke` and `delivery_smoke` examples. CI (`native-server.yml`) runs fmt, clippy and the tests with both features on Linux, Windows and macOS, a real Secret Service restart test on Linux (`scripts/keystore-smoke.sh`), and `delivery_smoke` against the server and PostgreSQL.

## `rv-signal`: the Signal protocol as WhatsApp speaks it

X3DH, the Double Ratchet and sender keys, with WhatsApp's wire messages (`msg`, `pkmsg`, `skmsg`, the sender key distribution message) and its stored records (`RecordStructure`, `SenderKeyRecordStructure` of `WAProto.proto`), for the Rust WhatsApp engine that replaces the Go helper ([decisions.md](../decisions.md)). It is written clean room, from Signal's X3DH, Double Ratchet and XEdDSA specifications and whatspec's protobuf schema, never from another implementation's source.

- **Storage stays with the caller.** A `SessionRecord` or `SenderKeyRecord` is loaded, one method runs, and the record is stored again only if it succeeded: a failure leaves it untouched (methods work on a copy). For a `pkmsg` the caller reads its prekey ids (`PreKeySignalMessage::deserialize`), looks up the key pairs, passes them in, deletes the consumed one-time prekey (`Decrypted::used_prekey`) and decides whether to trust the sender's identity key.
- **Behaviour matched to the other implementations where the specs leave room.** Signatures are made the spec's way (sign bit forced to zero) but verified both ways: other Signal implementations put the Edwards key's sign bit in the top bit of `s` (`curve.rs`). `previousCounter` is the index of the last message sent on the previous chain, not the spec's count. A new ratchet key is drawn only after the message that brings the peer's new key is authenticated.
- **Checked against an independent implementation.** `tests/oracle.rs` talks to a black-box oracle wrapping another library, in both directions (pairwise sessions with and without a one-time prekey, out of order, groups, curve operations), ignored unless `RV_SIGNAL_ORACLE` names the binary; the oracle is never committed. `tests/vectors.rs` replays its recorded runs (`tests/vectors/`, 109 steps) with both parties played by this crate, requiring the same ciphertexts byte for byte and the same random bytes drawn at the same steps.

## `rv-whatsapp`: the WhatsApp engine

[whatsapp-rust](https://github.com/oxidezap/whatsapp-rust) at `d73c3cc1`, MIT parts only, vendored in place of the Go helper (`apps/desktop/whatsapp/`, now Android's only) and later reshaped to the apps' architecture; `VENDOR.md` lists what was left out, what was added and why ([decisions.md](../decisions.md)). It keeps upstream's layout: the client (`src/`), the sans-IO core (`wacore`), the binary node codec, the Noise transport, the protobuf schema (`waproto`), SQLite storage, a Tokio transport and an HTTP client. Four crates are ours:

- **`wacore-signal`** is the Signal interface the engine calls, on `rv-signal` (re-exported as `wacore::libsignal`, the path the engine's code uses). Records are kept as WhatsApp's protobuf structures (a partial one is valid until it encrypts) and become `rv-signal` records for each operation. It carries two storage contracts of the engine's write-back cache:
  - **the counter lease**: a sending chain reserves its counters 64 at a time before one goes on the wire, and the raised lease must be stored first (`has_pending_reservation`, `is_wire_gated`); a record reloaded by the store instance that wrote it (same incarnation) is exact, any other reload moves the chain to the reserved ceiling, refused past 2,000. A record with no lease is stored as the bare `RecordStructure`;
  - **the session checkout**: an encrypt or decrypt takes the session out of the cache and works on a copy; success hands the new record back, failure or a dropped call (an aborted task) hands the original back unchanged.
- **`wacore-crypto`**: AES-GCM (the transport, in place), AES-CBC (in place), HMAC and SHA-2.
- **`wacore-appstate`**: the settings sync (app state), rewritten with WhatsApp Web's MAC rules; only its action catalogue is upstream's.
- **`rv-whatsapp-engine`** (`engine/`): the desktop helper. It speaks rv-core's JSON-lines protocol, the Go helper's frame for frame, over a whatsapp-rust client built with the in-memory backend (no SQLite linked: the default features are off). Its own projection keeps what the client is shown (messages, reactions, contacts and names, photos, unread counts), since whatsapp-rust has no message or contact store. The backend's snapshot (`InMemoryBackend::snapshot`, our addition) and the projection are sealed together into one file (`vault.rs`, AES-256-GCM, written through a temporary file under an exclusive lock), flushed from the client's write-behind caches first. The binary is `rv-whatsapp` (`main.rs`); `desktop-whatsapp.yml` builds it, Windows cross-built with mingw-w64.

Upstream's test suite runs as is: 5,449 tests.

## `rv-provider`, `rv-slack`, `rv-teams`: the provider clients

What talks to Slack and Teams moved out of rv-core so that the protocol code stands alone: tested, and later reusable, without the desktop's store, sessions or UI. A provider crate is the wire client (sign-in, requests, the live connection, translation into rv-provider's normalized types); rv-core keeps what writes its store (`slack::sync`, `teams::sync` and `teams::actions`), the outbox and the sessions.

- **`rv-provider`** holds what both providers and rv-core share: `rest` (`RestClient` with its four dialects; Slack's method allowlist and envelope live in `rest/slack.rs`, and `protected_url`), `socket` (`State`, `LiveEvent`, the websocket halves, `send` and `next_json`), `normalize`, `live` (presence and typing), `emoji` with its table, `text` (`decode_entities`, `is_web_link`) and `tls`. Its user agent names the app's version, which `rv_core::identify()` sets first thing in the GTK and Swift apps (`rocket-vibe-desktop/<version>` as before).
- **`rv-slack`**: token, browser and paired sign-in (`account`, `browser_login`, `handoff`), the directory, RTM (`live`), emoji names and `translate`. A login answers its own `Session`; `rv_core::slack` re-exports the crate and adds `login`, `login_at`, `login_paired`, `from_secret` and `client` over rv-core's `SessionInfo`.
- **`rv-teams`**: device-code sign-in and its `Tokens` (`auth`, holding rv-teams' `Session`), `client`, the Trouter feed (`live`, `frames`) and `translate`, plus the sign-in-only probes (`examples/teams-shapes.rs`, `teams-authz.rs`). `rv_core::teams` adds `session`, `approved`, `from_secret` and `set_credential_sink` over `SessionInfo`. Many Teams calls still sit in rv-core's `TeamsSync` beside its store writes; moving them down is the next cut.

## The bridges

- **`rv-crypto-mobile`**: a UniFFI (`=0.32.2`) facade for Kotlin, package `com.rocketvibe.crypto.engine`: a `CryptoInstallation` object, a `ProtectedKeystore` interface the app implements over Android's keystore, and modules for conversations, groups, history, identity, peers and recovery. `apps/mobile/modules/crypto-native/android/build.gradle` runs `build-android.mjs` before every build: `cargo rustc --release` for arm64-v8a and x86_64 (API 24, 16 KiB pages), then `mobile-bindgen` generates the Kotlin bindings into `android/build/generated/`, never committed. Tested by `--lib` in the crypto matrix, by Android instrumentation on an API 36 emulator (`native-crypto-android.yml`), and by the JS tests of `apps/mobile/providers/vibez/crypto*.test.ts`. See [mobile-native.md](mobile-native.md).
- **`rv-crypto-web`**: the same mobile facade without UniFFI, compiled to wasm with wasm-bindgen `=0.2.129` and an in-memory keystore the page seals: `Bridge` (`new`, `restore`, `snapshot`, `invoke`, `close`) plus `seal_file` and `open_file`. `npm run crypto:build` in `apps/web` builds it in Docker (`crates/rv-crypto-web/docker/Dockerfile`, whose wasm-bindgen CLI version must match the crate's pin) into `apps/web/src/crypto/wasm/`, committed with a manifest of source digests; the web build refuses a stale one and CI rebuilds and diffs it. See [web-client.md](web-client.md).
- **`rv-voice-mobile`**: RNNoise (`nnnoiseless`, the same pin as the desktop sidecar) behind three plain JNI functions for `apps/mobile/modules/voice`'s `Denoiser`, built by that module's `build-android.mjs`. It holds the repository's only `unsafe` outside the desktop shims, and no CI job runs its test; only the release APK build compiles it. See [voice](../features/voice.md).

## Footguns

- **A protocol change touches four places**: the Rust type, `docs/protocol/v1.schema.json`, the mobile `protocol.generated.ts` and the web copy. `check.sh` fails until the first three agree; the web build regenerates its copy.
- **A crypto change on the web needs Docker**: without `npm run crypto:build` the committed wasm no longer matches its sources and the web build refuses it.
- **Feature unification**: building `rv-ffi` alone and building the desktop workspace give `rv-crypto` different features; tests of the workspace see the union.
- **UniFFI is pinned exactly in `rv-crypto-mobile` (`=0.32.2`) but by caret in `rv-ffi`**: the locks keep them equal today; `cargo-locks.mjs` keeps them so.
