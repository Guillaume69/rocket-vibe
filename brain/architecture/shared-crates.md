# Shared crates: protocol, client, crypto

The Rust crates in `crates/` are shared by the RocketVibe server and the three client apps. They carry the native protocol (the RocketVibe server's own wire contract, not Rocket.Chat's), the HTTP client the desktop uses to speak it, and the MLS end-to-end encryption engine with its bridges to Android and the browser. Read [overview.md](overview.md) for where they sit, [server.md](server.md) for their main consumer, and the `e2ee-*` feature pages for what the encryption does for users.

## Workspaces and locks

The root `Cargo.toml` is a resolver-3 workspace of `apps/server`, `crates/rv-protocol`, `crates/rv-client` and `crates/rv-crypto-public`. Everything else keeps a workspace of its own, on purpose:

| Workspace | Why it stands apart |
|---|---|
| root | The server and the public crates it needs; the server never links the private vault. |
| `apps/desktop` | The desktop app ([desktop-app.md](desktop-app.md)); reaches the shared crates by path (`../../../../crates/...`), so its build container mounts the whole repository. |
| `apps/desktop/voice` | The voice sidecar, the only binary linking libwebrtc: kept out of the desktop's `cargo build --workspace`. |
| `crates/rv-crypto` | The private engine and its vault; its tests use their own `curve25519-dalek` optimisation profile. |
| `crates/rv-crypto-mobile` | A `cdylib` for Android, built per ABI by the mobile build. |
| `crates/rv-crypto-web` | The wasm build, with its own release profile (`opt-level = "s"`, LTO, `panic = "abort"`). |
| `crates/rv-voice-mobile` | A small JNI `cdylib` for Android, built apart like `rv-crypto-mobile`. |

Seven workspaces mean seven `Cargo.lock`. Within one semver-compatible line (`1.x`, `0.29.x`) a crate must resolve to the same version in all of them, so a fix to a shared dependency (crypto, TLS, tokio) reaches every app: `node scripts/cargo-locks.mjs` checks it (CI `cargo-locks.yml`), and `--sync` raises every lagging lock to the newest version already in use ([operations.md](../operations.md), [decisions.md](../decisions.md)).

## Who uses what

| Crate | Server | Desktop (`rv-core`, `rv-ffi`, `rv-gtk`) | Mobile | Web |
|---|---|---|---|---|
| `rv-protocol` | yes | `rv-core` | generated TypeScript types | generated copy of the mobile schema |
| `rv-client` | dev-dependency (tests) | `rv-core` (`rv-ffi` in tests) | | |
| `rv-crypto-public` | yes (verifies proofs) | `rv-core` dev-dependency, through `rv-crypto` | through `rv-crypto-mobile` | through `rv-crypto-web` |
| `rv-crypto` | never | `rv-core` (`native-http`, `system-keystore`), `rv-ffi` and `rv-gtk` (`system-keystore`) | through `rv-crypto-mobile` | through `rv-crypto-web` |
| `rv-crypto-mobile` | | | `modules/crypto-native` (Kotlin, UniFFI) | reused by `rv-crypto-web` |
| `rv-crypto-web` | | | | `src/crypto/wasm/` |
| `rv-voice-mobile` | | | `modules/voice` (JNI) | |

Cargo unifies features across a workspace: the three desktop crates all get `rv-crypto`'s `native-http` and `system-keystore` once any of them asks.

## `rv-protocol`: the wire contract

The native v1 types, with no UI, database or Rocket.Chat dependency (`VERSION = 1`, `crates/rv-protocol/src/lib.rs`). Modules follow the server's areas: `admin`, `bots`, `cards`, `commands`, `custom_emojis`, `e2ee` (the MLS transfer objects), `emojis`, `link_previews`, `live`, `markdown`, `parity`, `profiles`, `push`, `search`, `system`, `voice`, `workflows`.

- **Capabilities.** `Capabilities` is what discovery announces; every field added after v1 is `#[serde(default)]`, so an older v1 server reads as "not supported".
- **Shared rendering.** `markdown::parse` and `mention_names` are the bounded renderer both the server and the clients use; `emojis::canonical` reads `data/emoji-aliases.json`, generated by `scripts/generate-native-emojis.mjs` from the desktop emoji table.
- **One schema, three generated copies, all committed.** `cargo run -p rv-protocol --bin export-schema` writes `docs/protocol/v1.schema.json`. `scripts/generate-native-protocol.mjs` turns it into `apps/mobile/providers/rocketvibe/protocol.generated.ts` (types and a `nativeSchema` validator). `apps/web/scripts/sync-crypto.mjs` copies that into `apps/web/src/crypto/schema.generated.ts`. A second binary, `export-rendering-fixture`, writes `docs/protocol/native-rendering.fixture.json`.
- **Drift is a CI failure.** `apps/server/scripts/check.sh` diffs the exported schema against the committed one and runs `generate-native-protocol.mjs --check` and `generate-native-emojis.mjs --check`. Change a type, then regenerate both before committing.
- Tests: `tests/contract.rs` against `docs/protocol/v1.fixture.json`, plus `cards`, `link_previews`, `native_rendering`.

## `rv-client`: the HTTP client

`NativeClient` (`crates/rv-client/src/lib.rs`): one async method per server route (discovery, login and factors, email, push, voice, the `crypto_*` E2EE routes, about 170 in all). It takes an `http(s)` base URL with no user info, query or fragment, uses a 15 s timeout and no redirects, keeps the bearer token behind a mutex, and honours `Retry-After` per route (clamped to 1..300 s). No GTK, SQLite or keychain: the desktop's `rv-core::native` builds its session on it, and `rv-crypto`'s `native-http` feature drives the encrypted delivery worker with it. Tests run against a local listener (`src/crypto_tests.rs`) and through the server's integration tests, which use it as their client.

## `rv-crypto-public`: what the server can verify

The public halves of the encryption: account roots and device certificates (`Root`, `Device`, `Certificate`, `Revocation`), the group plans and transitions (at most 128 members and 256 devices), and the formats of archives, history shares, history backups, messages and recovery (`crates/rv-crypto-public/src/`). Everything is signed over `signing_bytes(domain, value)`, the domain, a NUL and the JSON, capped at 4096 bytes (`WIRE_LIMIT`). No private key, storage or trust decision lives here: the server uses it to refuse malformed or unsigned material without ever seeing a secret. Committed vectors in `fixtures/` are re-verified independently by `scripts/verify-*-vector.mjs` with Node and OpenSSL, in `check.sh` and in the Linux crypto job.

## `rv-crypto`: the engine

The client side of RocketVibe's MLS encryption (`crates/rv-crypto/src/lib.rs`): accounts and devices (`identity`, `account`, `installation`), key packages, groups and their messages (`groups`, `packages`), archives, files, history shares and backups, and the vault that holds all of it. It uses OpenMLS 0.9.0 with its RustCrypto provider, XChaCha20-Poly1305 and Ed25519, all pinned exactly; it invents no primitive.

- **The vault.** One encrypted SQLite row per account (WAL, `synchronous=FULL`, a 16 MiB document cap), sealed with XChaCha20-Poly1305 under a key held by the OS keychain (`keyring`, service `me.barrut.RocketVibe.crypto.v1`). Every transaction returns a checkpoint `(revision, SHA-256 of the sealed row)` that the caller must store in the keychain before using the result; opening refuses a database older than its checkpoint, so restoring an old copy of the file is detected. Only a crash between commit and keychain write is recoverable (`recover_committed`, one revision ahead). `protected::Manager` wraps the cycle with an OS lock; a concurrent opener gets `crypto_storage_busy`. The storage key is renewed every 30 days ([e2ee-storage-keys](../features/e2ee-storage-keys.md)). Model and invariants: `crates/rv-crypto/README.md`.
- **Features and targets.** `system-keystore` adds the OS keychain; `native-http` adds `rv-client` and tokio for the delivery worker. On `wasm32` the vault is a virtual SQLite snapshot sealed by the page with a non-extractable WebCrypto key under a Web Lock (`src/browser.rs`). On Android, file locking goes through `rustix`'s `flock`, since the standard library's is missing there.
- **Design notes** sit next to the code: `IDENTITY.md` (roots, certificates, revocations), `ENROLLMENT.md` (a new device proves possession, approval bound to the exact request), `MESSAGES.md`, `SETTLEMENT.md` (cancel or resume a send without a second POST), `RECOVERY.md` (root backup under a 32-byte recovery code), `JOURNAL.md`, `GROUP_COMMITS.md`, `GROUP_HTTP.md`, `GROUP_SETTLEMENT.md`, `PACKAGES.md`, `READMISSION.md`. The protocol specs are `docs/protocol/E2EE_*.md` and the plan is `docs/rfcs/0002-e2ee-native.md`.
- **What users get**: [e2ee-history](../features/e2ee-history.md), [e2ee-delegation](../features/e2ee-delegation.md), [e2ee-private-files](../features/e2ee-private-files.md), [e2ee-private-actions](../features/e2ee-private-actions.md), [e2ee-storage-keys](../features/e2ee-storage-keys.md). Rocket.Chat's own E2EE is a different scheme, in [e2ee.md](e2ee.md).
- Tests: inline `tests.rs` modules and the `protected_smoke` and `delivery_smoke` examples. CI (`native-server.yml`) runs fmt, clippy and the tests with both features on Linux, Windows and macOS, a real Secret Service restart test on Linux (`scripts/keystore-smoke.sh`), and `delivery_smoke` against the server and PostgreSQL.

## The bridges

- **`rv-crypto-mobile`**: a UniFFI (`=0.32.2`) facade for Kotlin, package `com.rocketvibe.crypto.engine`: a `CryptoInstallation` object, a `ProtectedKeystore` interface the app implements over Android's keystore, and modules for conversations, groups, history, identity, peers and recovery. `apps/mobile/modules/crypto-native/android/build.gradle` runs `build-android.mjs` before every build: `cargo rustc --release` for arm64-v8a and x86_64 (API 24, 16 KiB pages), then `mobile-bindgen` generates the Kotlin bindings into `android/build/generated/`, never committed. Tested by `--lib` in the crypto matrix, by Android instrumentation on an API 36 emulator (`native-crypto-android.yml`), and by the JS tests of `apps/mobile/providers/rocketvibe/crypto*.test.ts`. See [mobile-native.md](mobile-native.md).
- **`rv-crypto-web`**: the same mobile facade without UniFFI, compiled to wasm with wasm-bindgen `=0.2.129` and an in-memory keystore the page seals: `Bridge` (`new`, `restore`, `snapshot`, `invoke`, `close`) plus `seal_file` and `open_file`. `npm run crypto:build` in `apps/web` builds it in Docker (`crates/rv-crypto-web/docker/Dockerfile`, whose wasm-bindgen CLI version must match the crate's pin) into `apps/web/src/crypto/wasm/`, committed with a manifest of source digests; the web build refuses a stale one and CI rebuilds and diffs it. See [web-client.md](web-client.md).
- **`rv-voice-mobile`**: RNNoise (`nnnoiseless`, the same pin as the desktop sidecar) behind three plain JNI functions for `apps/mobile/modules/voice`'s `Denoiser`, built by that module's `build-android.mjs`. It holds the repository's only `unsafe` outside the desktop shims, and no CI job runs its test; only the release APK build compiles it. See [voice](../features/voice.md).

## Footguns

- **A protocol change touches four places**: the Rust type, `docs/protocol/v1.schema.json`, the mobile `protocol.generated.ts` and the web copy. `check.sh` fails until the first three agree; the web build regenerates its copy.
- **A crypto change on the web needs Docker**: without `npm run crypto:build` the committed wasm no longer matches its sources and the web build refuses it.
- **Feature unification**: building `rv-ffi` alone and building the desktop workspace give `rv-crypto` different features; tests of the workspace see the union.
- **UniFFI is pinned exactly in `rv-crypto-mobile` (`=0.32.2`) but by caret in `rv-ffi`**: the locks keep them equal today; `cargo-locks.mjs` keeps them so.
