# Login and servers

How a user signs in to a Rocket.Chat server (password, then a second factor when the server asks), how the session is kept and resumed, when it ends, and how several servers or accounts live side by side. Both apps follow the same server contract; they differ in where secrets live and in how many accounts one server may hold.

## The shared flow

0. **Server type.** Under the address, a selector offers Automatic (the default), Rocket.Chat or Vibez. Automatic asks `/.well-known/vibez` first and treats only a 2xx naming the product as Vibez; any other answer (404, or the 403 of a proxy that forbids `/.well-known/`, as on chat.barrut.me) falls through to the Rocket.Chat probe below. Rocket.Chat skips the native discovery; Vibez requires it and never falls back ("no Vibez server at this address"). Changing the choice probes again. Core: `ServerKind`, `native::probe_as`, `server::probe_as`, `session::login_as` (`rv-core`); `ServerChoice` over `rv-ffi` (`Client.probe`, `login`, `is_native_server`); mobile `discoverServer(..., kind)` and `NotVibezError` (`lib/serverKind.ts`).
1. **Probe.** Before any credential, the client reads two anonymous routes in parallel: `GET /api/info` (outside `/api/v1/`, it returns the minor version only, `8.5`, and proves the server is a Rocket.Chat) and `GET /api/v1/settings.public?count=0` (`count=0` disables paging). From the settings it learns whether the password form is offered (`Accounts_ShowFormLogin`), whether 2FA and E2EE are on, and which OAuth providers are configured. The server address is normalised first: `https://` is assumed when no scheme is typed, a trailing slash is dropped, and a sub-path (a server behind a proxy at `/chat`) is kept.
2. **Login.** `POST /api/v1/login` with `{user, password}`, sent anonymously. The answer carries `authToken`, `userId` and `me.username`. A body without token or user id is treated as a failure, not a session. The field is labelled "Username or email" in every app: Rocket.Chat and Mattermost take either, and a Vibez server (`POST /api/v1/auth/start`, `{username, password}`) resolves an identifier containing `@` through the account's verified address (`password_login` in `apps/server/src/auth.rs`); the apps send it as typed and name the account by the session's `user.username`. The recovery-code and invitation forms of a Vibez server take a username only.
3. **Second factor.** When 2FA is required the server answers with a `totp-required` error whose `details.method` names what it wants: `totp`, `email` or `password`. The client does not guess the method; it reads it. The code is resent with the same login, in the `x-2fa-code` / `x-2fa-method` headers. For `email`, a `codeGenerated: false` flag means no mail left yet, so the client calls `users.2fa.sendEmailCode` first. For `password`, the expected code is the SHA-256 hex of the password, never the clear password.
4. **Resume.** The same `authToken` serves REST and the DDP socket (`method login {resume}`), so a stored session needs no new login at launch.
5. **End.** Only a 401 that is a real Rocket.Chat answer ends a session (see [rocket-chat.md](../architecture/rocket-chat.md) for why 401 is safe to trust and why `/api/v1/login` itself must be excluded). Sign-out sends `POST /logout` best effort: the local state is signed out whatever the server says.

## Mobile

**Screen.** `app/login.tsx` is a three-phase state machine (`Phase`: `server`, then `credentials`, then `twoFactor`). The REST client lives inside the phase variants, so it exists exactly when a server was validated. A ref (`inFlight`) guards re-entry: two events in the same frame (Enter key plus a tap) would otherwise send two logins and burn the same one-time TOTP code twice. The probe (`probeServer` in `lib/server.ts`) goes through `RestClient` with the `outsideApiV1` option, which gives it the maximal timeout; on a bare `fetch` a hanging proxy left the screen dead. When `Accounts_ShowFormLogin` is false the screen warns but does not block, since the API sometimes accepts a direct login anyway. The probe also records `Site_Url`, which the login answer lacks: it is merged into the persisted `Session.siteUrl` and later used to build quote permalinks (`lib/quote.ts`). Errors map to messages: a repeated `totp-required` on the same method or a `totp-invalid` means "code refused", a plain 401 means "credentials refused". The email method gets a "send the code" button, then a "resend" link.

**Default server.** `DEFAULT_SERVER` (`db/migrate.ts`) is `http://localhost:3000` in dev builds and `https://chat.barrut.me` otherwise; the field is pre-filled with the last server used unless the user already typed something.

**Storage.** `lib/sessionStore.ts` keeps everything in `expo-secure-store` (Android Keystore), never AsyncStorage. Key names are derived in `lib/storageKeys.ts`, isolated so tests can prove the isolation rules:

- the session is keyed by **server only**: `session-<first 32 hex of SHA-256(url)>` (Keystore keys accept only `[A-Za-z0-9._-]`). One account per server on mobile;
- the E2EE private key is keyed by **(server, account)** (`e2e-<hash of url|uid>`); an old server-only key is never read, only deleted at startup (`purgeAllLegacyE2EKeys`), because reading it re-imported one account's key for the next;
- `last-server` points at the session to resume, `known-servers` lists every server that ever held a session (the Keystore cannot enumerate its keys), `device-push-token` remembers the FCM token for sign-out and `pending-logouts` queues interrupted sign-outs (each entry's token under `pushToken`);
- these fixed key names are `STORED_KEYS` in `lib/storageKeys.ts`. Before migration 0016 they had French names (`dernier-serveur`, `serveurs-connus`, `jeton-push-appareil`, `deconnexions-en-suspens`); `readMovedKey` moves a value still under its old name on first read, writing the new key before deleting the old, so an upgrade keeps the session pointer, the server list and pending sign-outs. A pending-logout entry written with the old field `jetonPush` is still read;
- on iOS the entries are written `AFTER_FIRST_UNLOCK` so the notification service extension can read them with the phone locked.

`readSession` treats corrupt or foreign entries as absent and migrates old shapes on read (`kind`, formerly `genre` and still read under that name, defaults to `rocketchat`; `siteUrl` to null). Accounts saved on a Vibez server before its rename (kind `rocketvibe` on mobile, genre `rocketvibe` in the desktop keychain) are not migrated, in any app: they are added again by hand.

**Lifecycle.** `ui/session.tsx` (`SessionProvider`) exposes `SessionState` (`phase`: `starting`, `disconnected`, `connected`). At launch it resumes **optimistically**: the stored session is declared connected at once and `resumeSession` validates it in the background. An unreachable server keeps the session; only `isTokenRejected` (a 401 with a Rocket.Chat envelope, not a 2FA challenge) signs out, and it also adopts a username changed elsewhere. Every client of the running app is made by `clientFor`, which wires `RestClient.onTokenRejected` so any call that meets a revoked token triggers `revoke`. Two guards protect a fresh session from a late 401: the token in flight is compared with `currentToken`, and the Keystore is re-read before anything is erased. Sign-out unregisters the push token and calls `logout`; if either fails offline, the pair is queued (`addPendingLogout`) and replayed at the next start by `finishPendingLogouts` (`lib/deferredLogout.ts`), because the token is still alive server-side and keeping it is the only way to kill it. `clearTraces` then removes the session, the E2EE key and the legacy key together. The per-account SQLite file is not removed by this path.

**Several servers.** Each server keeps its own session; the local database is per (server, account) (`db/fileName.ts`: `rocket-vibe-<host slug>-<uid>.db`). Settings has a "change server" link to `/login?change=1`, which lists the known servers; tapping one calls `switchServer`, which reads the target session before moving the resume pointer (so a server without a session never strands the user signed out) and validates it in the background. A notification deep link carrying `?host=` for another server lands on an explicit "switch to that server" screen in `app/room/[rid].tsx` (`OtherServer`) rather than switching silently. See [sharing-and-links.md](sharing-and-links.md).

**Server rail.** The home screen draws a column down its left edge (`ui/serverRail.tsx`, in `app/index.tsx`): a tile per known server that still has a session (`listKnownServers` then `readSession`), the open one outlined, then "+" to `/login?change=1`. A tile shows the server's own icon when it has one (`lib/serverIcon.ts`, see Server icon below), else the host's initial. A tap calls `switchServer`; tiles keep the `known-servers` insertion order when selection changes. Settings > Accounts can hide the column (`ui/serverRailSetting.ts`, SecureStore `hide-server-rail`, off by default); the page's Change server link then stays the way to switch or add a server, and the other servers' unread dots are not read. Only the open server is connected; while the home screen is focused and the app in the foreground, each other server is read once a minute and at each return to the foreground: `subscriptions.get` for Rocket.Chat, `GET /api/v1/rooms` after `prepareNativeSession` (which renews the token under its lease) for Vibez, judged by `lib/accountUnread.ts` (the desktop rule: an open subscription with unread or an alert; a read state with `readBadges(..).alert`). A token refused there never signs anything out. A push for another server that reaches JS (`setNotificationHandler`, so iOS in the foreground) lights the dot at once through `ui/serverDots.ts`; Android message pushes are posted by our Kotlin service and never reach JS, so there the dot waits for the next read.

**Server icon.** Read without signing in for every account of the rail, once per server and app session (each visit would cost an anonymous `settings.public`, rate limited per address), with a 10 s timeout, and again after an administrator changed it here (`forgetServerIcon`): Rocket.Chat's `favicon_192` asset when an administrator set one (`settings.public?_id=Assets_favicon_192`, `value.url`; only `defaultUrl` means the stock logo, which is not the server's own), its URI carrying the time of that read as `?rv=` (ignored by the server) because Rocket.Chat serves it at a fixed URL with no ETag; Vibez's instance icon at `/api/v1/instance/icon?v=<icon_revision>` from the discovery document. Mattermost and kChat keep the initial. `serverIconUri` answers a URI, `null` (no icon: the initial) or `undefined` when the read concluded nothing (unreachable, refused), and then the rail keeps the icon it shows. Changing it is administration ([administration](administration.md#server-icon)).

## Desktop

**Core.** `rv-core/src/server.rs` (`probe`, `ServerProfile`) and `rv-core/src/session.rs` (`normalize_server`, `login`, `two_factor_code`, `request_email_code`) implement the same contract. `normalize_server` rejects input without a host. `SessionInfo` holds base URL, user id, username and token. `Session::start` opens the store, starts DDP with the token and spawns `watch_token`, which turns a token refusal from `RestClient::token_rejected` into `SessionEvent::Expired` only when the refused token is the session's own.

**GTK login.** `rv-gtk/src/login.rs` probes 600 ms after the server field stops changing (a generation counter drops stale answers) and shows one line: version, "2FA", "E2EE", or a warning when the password form is off. The code step adapts its caption to the method and masks input for `password`. `window.rs` drives it: `submit_login` keeps a `PendingLogin`, re-sends with the code, and when an email challenge reports no generated code it calls `request_email_code` on its own. There is no explicit resend button in the GTK code step. Errors map by status (0 unreachable, 401 bad code or rejected, 429 too many tries). The default server is `https://chat.barrut.me`, overridden by the `last-server` file.

**Storage.** `rv-gtk/src/secrets.rs` keeps one keychain item per **account** (`account_key` = `<base_url>|<user_id>`): Secret Service via `oo7` on Linux, Credential Manager or Keychain via the `keyring` crate elsewhere, with an index file because those cannot list items. Plain files under the config dir `rocket-vibe-rs/` hold the active account (`active-account`), the known servers (`servers`, most recent first, capped at 8) and `last-server`. Keychain calls time out after 5 s so a silent keyring cannot freeze the splash screen. The E2EE key (JWK) rides in the same item while unlocked. The database is `<host>[_port]-<uid>.sqlite` in the data dir (`database_path`).

**Several accounts.** Because the key includes the user id, desktop can hold two accounts on one server, which mobile cannot. Settings (`settings.rs`, `accounts_group`) lists every keychain account, switches on a click (`switch_to`) and offers "add account" (`add_account`), which keeps the current account as `previous` so the login page can cancel back to it. Sign-out removes the keychain item, sends `logout` (Mattermost `users/logout`, kChat nothing: its token is Infomaniak's), deletes the database files (`stop_session(true)`) and hands over to the next stored account if any. `Session::logout` answers whether the sign-out settled (done, or the token already refused); when the server could not be reached, the session is kept in the keychain under `logout|<server>|<user id>` with `pendingLogout: true` (`session::pending_logout_key`, `pending_logout_secret`; GTK `secrets::keep_logout`, rv-ffi `accounts::keep_logout`, the same index file on macOS), never listed as an account, and replayed at the next start (`Session::replay_logout` from GTK `secrets::replay_logouts` and rv-ffi's `Client::new`), which forgets it once settled, as mobile's `finishPendingLogouts` does. A native Vibez sign-out that fails keeps the account signed in and says why instead. An expired session does the same and shows the login page with an "expired" message. `open_link` switches to the account whose server fits a link.

**Server rail.** `rv-gtk/src/rail.rs` puts a column left of the chat page (`window.rs` wraps the chat widget with it): a tile per keychain account, the open one outlined in pink, "+" (`add_account`), and a yellow dot on an account with unread messages. `refresh_rail` rebuilds it after every session start from `secrets::load_for_rail`, which keeps the original tile positions independent of the open account. GTK and SwiftUI share the non-secret `server-rail-order` file: `rv_core::server_rail::order` captures the initial keychain/index order, keeps it across restarts and appends new accounts; removed accounts disappear. `secrets::load_all` and rv-ffi's `Client.accounts` still return the active account first for startup, while SwiftUI renders `AppModel.railAccounts` in the saved rail order. Selecting a tile changes only its outline. Desktop only (user decision, 2026-10-13), a tile dragged onto another takes its place, after it when moving down and before it when moving up (`server_rail::reordered`), and `server_rail::save` writes the new order to the same file: GTK `Rail::reorderable` puts a `gtk::DragSource` (the account key as a string, the tile as the drag icon) and a `gtk::DropTarget` on each button, then rebuilds the rail once the drop is over; SwiftUI `ServerRail` uses `.draggable` / `.dropDestination` and `AppModel.moveRailAccount` over rv-ffi `Client.moveRailAccount`. Ctrl + 1 to 9 opens the rail's first nine accounts and Ctrl + 0 the tenth (`server_rail::shortcut_slot`), in the rail's order and with the rail hidden too, as a click on the tile would (nothing on the open one). GTK: a capture-phase key handler on the window (`AppWindow::new`) ignores it on the sign-in page and under a dialog; `rail::shortcut_digit` also reads the digit the same physical key types with Shift, so the unshifted AZERTY digit row works, and leaves Shift, Alt and Super combinations alone (Ctrl+Shift+7 to 9 format the composer). Each tile's tooltip names its shortcut (`gtk::accelerator_get_label`). SwiftUI: Cmd + digit, one menu command per account in `AppCommands` (not over a panel), its tooltip saying `⌘n` (rv-ffi `rail_shortcut_digit`). Every tile has a menu (a right click or a long press; desktop only, user decision 2026-10-13): the open account's administration for an administrator, then **Mute** with 1 hour, 4 hours, until tomorrow 09:00 (`reminders::tomorrow_at_nine`), a week or until unmuted, or, while muted, the mute's end and **Unmute**, and **Log out** last, in red, behind a confirmation whose backdrop is Cancel. `rv_core::account_mute` keeps the mutes in the config dir's `muted-accounts` (`<account key>\t<end ms | forever>`), forgetting ended ones when read. A muted account keeps syncing, but `AppWindow::notify` / `notify_background` show nothing for it, `ring_background` does not ring for it, the open account's call prompt shows without its ringtone (`chat_call_ring.rs`, `chat_voice.rs`), and `Rail::set_muted` / `badge::set_muted` hide its dot, dim its tile with a muted mark and leave its count out of the app badge; `AppWindow::apply_mutes` re-reads the file after each change and again when the earliest timed mute ends. Log out of the open account is the account menu's sign-out, which now also ends its mute (signing in again starts unmuted); another account (`AppWindow::logout_account`, then `forget_account`) cannot be opened while it runs (`leaving`, checked by `switch_to_for_link`), has its background ring ended, is told to its server (a Vibez or WhatsApp refusal keeps it and says so), removed from the supervisor, its downloaded files (`cards::clear_file_cache`) and store closed and deleted (cleared for Vibez), its keyring entry, reminders and mute gone, then the rail is read again. An account with no running session (expired, or never started) has nothing to tell its server now: a Rocket.Chat or Mattermost token is left to `keep_logout` for the next start, and its stored messages are deleted all the same. Notifications, rings and the badge read the mutes from memory (`rail::mute_of`, refreshed by `rail::mutes` in `apply_mutes`, which also runs whenever the window comes to the front, since the end timer counts awake time only) and compare a timed mute's end with the clock. Ctrl+Shift+A sits in the same window key handler as Ctrl + digit, and `shortcut_digit` only falls back to a key's shifted digit for a symbol key, so a keypad key without NumLock (Ctrl+End) keeps moving the cursor. SwiftUI: `ServerRail.menu` (`.contextMenu`, a `Menu` of `mute_choices`, `confirmOverlay` for Log out), `AppModel.mute` / `unmute` / `refreshMutes` (first run by `keepAccountsConnected`, so a hidden rail still applies the mutes; its wait capped at a day) / `isMuted` (the in-memory `mutedAccounts`) / `signOut(_:)` (an account being signed out cannot be switched to; the account menu's `signOut()` ends the open account's mute) over rv-ffi `Client.muteAccount`, `unmuteAccount`, `accountMute`, `mutedAccounts`, `nextMuteEnd` and `signOutAccount` (`rv-ffi/src/account_menu.rs`, which also signs out an account that is not running, as GTK does); the sheets of the room list close when the account changes (a Cmd + digit under a sheet); background notifications and calls of a muted account are dropped in `handleAccount`, the open account's in `handle(.incoming)` and the ringtones in `RocketVibeApp` (`openMuted`), and the dock count leaves muted accounts out (`showAttention`). A tile shows the server's own icon when it has one (`rv_core::server_icon::fetch`, the same rule as mobile), read on each rebuild and kept between rebuilds so it does not flicker; `rail::reload_icons` reads them again after the administration changed one. A read gives `server_icon::Icon`: `Image` (a PNG or JPEG recognised by its first bytes, whatever the `Content-Type`, at most 2 MiB however long the response), `Absent` (the initial) or `Unknown` (unreachable, refused, too big, not an image), which keeps the shown icon. GTK decodes it as a center-cropped square at most 88 px wide (`rail::icon_texture`, twice the tile) and draws it with `rail::icon_image`, a `gtk::Image` of `pixel_size` 44 (a `gtk::Picture` would measure its texture, twice the tile), which the Dashboard's preview reuses. SwiftUI reads them into `AppModel.serverIcons` with the account list over rv-ffi `Client.serverIcon`, which returns the same three cases (`enum ServerIcon`; `.unknown` keeps the entry). The dots are live: every signed-in account stays connected in the background (`rv_core::supervisor`, see Background accounts below), and each account's store gives its unread state (`supervisor::badge`, the room list's rule: an open room with unread messages or an alert), sent as `Notice::Unread` when it changes; GTK `Rail::set_unread` from `AppWindow::on_notice`, SwiftUI `AppModel.unreadAccounts` from `handleAccount` over rv-ffi's `AccountEvent::Unread`. The app badge adds every account's count (GTK `badge::set_account`, SwiftUI `AppModel.showAttention`). Settings > Accounts can hide the rail ("Hide the server bar", off by default): GTK `Rail::set_hidden` and SwiftUI `AppModel.setRailHidden` share the file `hide-server-rail` in the config dir, whose presence hides it; the accounts list of that page still switches and adds. SwiftUI keeps the account refresh and `keepAccountsConnected` in `ChatView`, not in the rail, so that list stays fresh with the rail hidden.

**Background accounts.** Every signed-in account of the desktop stays connected, not only the open one (`rv-core/src/supervisor.rs`, `Supervisor`). It holds one `provider::Chat` per account key (`<base URL>|<user id>`, the keychain files' key): `open(info)` returns the running session (a suspended Vibez session connects again) or starts one and makes it the open account; `sync(accounts)` starts the missing ones in the background (a failed start is tried again after 1, 2, 4 s... up to 5 min) and stops those signed out elsewhere; `remove(key)` takes one out for a sign-out or an expiry; `set_active` says which one is on screen, and the one leaving it closes its open room (`Session::close_room`, so its per-room streams stop) and leaves its voice session. Each session keeps reconnecting on its own (DDP, Mattermost or kChat socket, Vibez live socket, each with its back-off). A watcher per account turns its `Chat::events()` into `AccountNotice`s, through the pure rule `step`: a message to notify (`Notice::Incoming`, already filtered by that account's rules: room and account preference, silenced rooms, mentions only, do not disturb), its ringing call (`Notice::Call`, Rocket.Chat or kChat, from `Session::incoming_call`) or Vibez voice ring (`Notice::Voice`, `supervisor::voice_call`), its unread state (`Notice::Unread`, after 300 ms of quiet) and its expiry (`Notice::Expired`: stopped, not started again until opened). The open account's messages, calls and expiry are left to the window's own listener, so nothing is announced twice. GTK's `AppWindow` opens every account through it (`start_session`, `refresh_rail` syncs, `stop_session(false)` leaves the account running, `stop_session(true)` removes it); rv-ffi's `Client` does the same (`background.rs`: `Client.resume` and `nativeResume` reuse the running session, `Chat.shutdown` and `NativeChat.shutdown` only detach, and take the account off screen (`Supervisor::leave`) only if no account, the same one included, was opened since (`open_counted`); SwiftUI's closed `MediaStore` then vouches for no image of it, `watchAccounts`, `keepAccountsConnected`). See [notifications](notifications.md#desktop) and [calls](calls.md#ringing) for what a background account shows.

**SwiftUI (macOS).** `LoginView` and `RocketVibeKit/LoginModel.swift` repeat the GTK flow over `rv-ffi` (`Client.probe`, `login`, `requestEmailCode`). `rv-ffi/src/accounts.rs` stores accounts exactly where rv-gtk keeps them on macOS (same Keychain service, same files, same database names), so the two macOS apps share sessions. `AppModel` resumes the first account and falls back to the next on sign-out or expiry.

## Web

The Vibez login and second-factor steps use actual GTK captions, including localized password, invitation and recovery refusals rather than wire error keys. The factor form offers Authenticator app, Email code or Backup code, a 34-pixel method selector, the method-specific introduction and code label, and the 62-pixel Confirm action. A refused code, expired or unavailable factor, unreachable server, exhausted retry budget or unavailable protected storage uses the native error caption. Unknown technical failures fall back to a native contextual caption. An unfinished sign-in displays GTK's hint that an already accepted sign-in can be confirmed without a code.

`src/factor-auth.ts` saves the finish operation and successor token before verification, then always replays that exact pair. A blank-code replay retrieves a committed answer instead of consuming a second one-time code. Email is explicitly Send code, Resume delivery and Resend code: the original delivery/operation/challenge IDs are saved before sending, Resume probes their receipt, and Resend first resolves that original receipt and obeys its actual cooldown. The current delivery status remains visible. No new server route or protocol shape is involved.

`src/factor-auth-vault.ts` seals those receipt intents with the existing AES-GCM nonextractable-key envelope. Its operations key starts with the full instance/epoch/user account prefix and includes the challenge ID; authenticated data also binds the origin, instance, epoch, user and login-factor purpose. Ordinary outbox and renewal pumps cannot interpret the record as a send intent. Entered passwords and factor codes are never persisted; successor tokens are ciphertext within the envelope. Named locks and challenge-object/account/token/generation checks fence delayed encryption, storage and HTTP answers. Back and accepted sign-in retire the exact challenge record and its key; normal account logout purges that account prefix. A legacy unsealed finish pair is validated and moved into the private envelope before it is used.

`tests/factor-auth.mjs` qualifies real committed lost verification answers followed by blank original replay, one backup-code consumption, native refusal and saved-finish captions, account purge, Back retirement, real TLS email delivery with a lost response, exact Resume IDs, no duplicate mail and real resend cooldown. Model/vault units cover storage-before-side-effect, account/challenge binding and held encryption, commit, read and lock retirement fences. Render evidence is separately identified in `docs/WEB_GTK_SCREEN_MATRIX.md`.

One account on the serving origin ([web-client](web-client.md)). Sign-out (`App.logout` in `apps/web/src/app.ts`, `logoutSession` in `src/session.ts`) finishes a pending session rotation, sends `POST /api/v1/auth/logout` with its own transport and then always purges the account from IndexedDB (`purge`). Its result is `revoked` (done, or a 401 `session_rejected`), `deferred` or `refused`. `deferred` is a server not reached (`logouts.ts#logoutOutcome`: no answer, a timeout, a 5xx, 408, 429, or a 401 without the server's `session_rejected` code, which a proxy could have sent): the session's token, plus the `next_token` of a rotation intent that may have committed, goes to the `logouts` store (IndexedDB version 6) as `{id, tokens, expires}`, nothing else, never purged with the account and never shown. The expiry is the session's, or 30 days from now for a successor (`SESSION_DAYS`, the server's session lifetime). A toast says the server will be told when reachable. `finishPendingLogouts` replays each entry at the start (`App.init`), on the browser's `online` event and when the sync socket opens: a settled token (success, `session_rejected`, any other refusal) leaves the entry, an unreached one keeps it, an entry past its expiry goes without a request; one run at a time per tab, and across tabs under the `rv-logout-replay` Web Lock. Unit tests: `tests/logouts.test.ts`, `tests/session.test.ts`; browser test `tests/logout-replay.mjs` (the request blocked by Playwright routing, then allowed: the token answers 401 after the replay, online and at the next start).

## Parity

[parity](../parity.md) §1 is done on desktop except email 2FA, which is partial: GTK and SwiftUI request the code automatically and have no resend control. Other differences worth knowing: mobile holds one account per server, desktop several; mobile keeps the database on sign-out, desktop deletes it (the `.sqlite`, `-wal` and `-shm` files, `Store::remove_files`, after `Store::close` has released the file that tasks still running hold, which Windows would otherwise refuse to delete); mobile and desktop replay failed Rocket.Chat, Mattermost and kChat sign-outs at next launch; desktop persists the revocation marker in the keychain. A failed native Vibez sign-out keeps the account signed in.

## Quick server-bar control

GTK and SwiftUI keep a server-bar button at the start of the room-list header, reachable when the bar is hidden. It changes the same device preference as Settings > Accounts, immediately and for the next launch. GTK updates its tooltip and tint when either entry changes the preference. The Linux title-bar layout keeps the desktop's minimize, maximize and close controls but omits its extra app-icon slot.

Mobile keeps a labelled, 44-point server button in the home header. Settings moves to the bottom account bar so the header fits while the rail is visible on a narrow phone. The hidden bar stays recoverable from that header button and Settings > Accounts. Web has one account on its serving origin and no server bar.
