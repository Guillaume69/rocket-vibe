# WhatsApp account

A personal WhatsApp account linked by scanning a QR from the official phone app, the way WhatsApp Desktop is: the computer becomes a linked device with its own keys, and the account then lives in RocketVibe like any other (rail, room list, timeline, composer, notifications). It is a local third-party implementation of the linked-device protocol (whatsmeow), not Meta's Business API, and nothing goes through a Vibez server ([decision](../decisions.md#whatsapp-through-a-local-linked-device-helper-2026-10-12)). Desktop (GTK), and Android in part; work on `claude/whatsapp-feasibility`, live-tested by the user on Windows. Protocol details and the verification record: [the handoff](../../docs/WHATSAPP_HANDOFF.md).

## Desktop

**Helper.** A Go process (`apps/desktop/whatsapp/`) per account, beside the app (`rv-whatsapp`, or `RV_WHATSAPP_HELPER`). Its engine (the `engine/` package, exported surface in `engine/api.go`: `Open`, `Device.Connect`, `Handle`, `Close`, a frame `Sink`) is transport-free, so the Android app can bind the same code with gomobile; `main.go` speaks JSON lines over private pipes. A `replay` command re-emits the cached projection from a `reload`, for a client attaching to an engine already running. Its SQLite stays in memory and reaches disk only sealed with AES-256-GCM (`vault.go`) under a key from the system keychain, one entry per account; a state without its key fails closed. Restoring goes through SQLite's backup API, since a deserialized image cannot grow.

**Account.** A `SessionInfo` with `base_url = whatsapp://<state id>`, `user_id` = the account's JID, no token, genre `whatsapp` in the keychain (`rv-core/src/whatsapp.rs`, `native.rs`); older builds and the SwiftUI app skip it. Places that read `base_url` as an http server check `whatsapp::is_whatsapp` first. `WaSession` (`rv-core/src/whatsapp_session.rs`) keeps the helper alive (restarts with back-off once the old one released its state lock), builds `RoomRow`s and the timeline from its snapshot, and is `provider::Chat::WhatsApp`: the supervisor counts its unread chats and keeps it connected in the background like any account.

**Adding.** WhatsApp is the last of the login page's server kinds (listed when the helper is installed, `WHATSAPP_KIND` in `rv-gtk/src/login.rs`); choosing it puts the previous kind back and opens a dialog with the QR on a new state (`rv-gtk/src/whatsapp_link.rs`); closing it abandons and erases that state. Its "Link with a phone number" section is the camera-free way, the one a phone linking itself needs: the number (digits only, international) goes to the helper's `pair_phone`, whatsmeow's `PairPhone` asks WhatsApp for an 8-character code (`whatsapp/engine/pairing.go`, presented as a Chrome on the host's OS), shown as `XXXX-XXXX` to type on the phone under Linked devices, Link with phone number instead. The QR attempt keeps running beside it; a refused number (`phone_invalid`) or no code (`pairing_code_failed`) is an ordinary, non-fatal error that re-enables the button. The device the earlier pilot window linked (`whatsapp-pilot/`) is adopted once at startup as the account `whatsapp://pilot`, its state and key left in place.

**Chats** (`rv-gtk/src/chat_whatsapp.rs`). Names resolved when shown, from the name table the helper refreshes as contacts sync (address book, push name, business name, group subject, else the number); a phone number and its LID make one conversation once WhatsApp maps them (`store.go`, `normalize`). Profile photos on tiles, beside messages and for my own account. Reactions (chips, quick reactions in the message menu), quoted replies (native quote card, Reply in the menu), my own messages edited in place (15 minutes) or deleted for everyone (48 hours, confirmation that closes on a backdrop click). Unread counts shared with the phone; the open chat is read while the window has the focus, with read receipts unless my privacy settings send none; Delivered, Read or Played under my latest message. New conversation searches the phone's contacts and groups, or a typed number WhatsApp confirms; the chat opens before its first message. Attachments (images, stickers, GIFs and videos, audio and voice notes, documents) are kept with their caption, size, dimensions and thumbnail; a third media provider (`media::Provider::WhatsApp`, paths `wa-media:<message id>`) has the helper fetch and decrypt one on first use into the account's private folder, gone with the account, and the timeline's own rows draw them (image in place, playable audio card, video card, document with Open and Save). Link previews come from the sender's app, never from fetching the page (WhatsApp recipients do not): the helper keeps the message's `matchedText`, title, description and inline JPEG thumbnail (`linkOf`, `engine/engine.go`), an edit replacing them, and serves the thumbnail through `download` (`linkImage`, `engine/media.go`); the client turns them into a `urls` entry (`WireMessage::link_preview`, `ogImage` = `wa-media:<id>`), so the timeline's generic link card draws it, and a YouTube, Dailymotion or Vimeo link gets its video card with the sender's thumbnail instead of the site's (`content::video_links`). A received preview's large thumbnail, when the sender uploaded one, is fetched with `DownloadThumbnail` (the inline one stands in meanwhile, not kept). My own texts get a preview the way WhatsApp's apps make one (`engine/preview.go`): the first link, as typed, is fetched from this device (public addresses only, never the local network; 10 s, 512 KB of page, 5 MB of image, five redirects), its Open Graph or Twitter title, description and image become the extended text's `matchedText`, title, description and a 160 px inline JPEG, and a 720 px JPEG is uploaded as a `thumbnail-link` for the recipients and kept as my card's picture. A page that gives nothing sends the plain text. The preview is made after the message shows as sending, so texts go through an ordered queue (`sender`) rather than the command loop. A send is recorded before its network attempt; its text comes back as a draft only when it provably never left, and an unconfirmed one is never sent again. Notifications for new messages (not what was there when the helper connected), whose quick actions work for WhatsApp too: a reaction, mark read, an inline reply (`window.rs`, `whatsapp_notification`). "Alice is typing…" in the open chat and my own typing sent; the account is online only while the window is in front with it open, like WhatsApp Web, since WhatsApp holds the phone's notifications back while a device is online. Unlinking from the account menu asks WhatsApp to forget the device; a failure keeps the account, an unlink from the phone ends it.

Sending files goes through the composer's attach and microphone buttons (`attach::send_all_whatsapp`): one file at a time per chat, pictures reduced unless the original is asked for, a recording made here sent as a voice note (Ogg/Opus, its length read from the stream), MP4 as video, other audio as audio, anything else as a document; the helper uploads first (a failed upload is a plain refusal) and keeps my copy so it shows at once (`upload.go`).

**Calls** ring here (`calls.go`; `Notice::Ring` / `RingEnded` of `WaSession`, watched by the window for every WhatsApp account, open or in the background): the incoming-call prompt and ringtone name the caller, Decline rejects the call for all my devices, "Answer on the phone" only stops it ringing here, and it closes when the call ends or is answered elsewhere. Audio and video are not carried: whatsmeow implements none of WhatsApp's VoIP, and rebuilding that proprietary protocol is out of scope.

**Hidden** because WhatsApp has no equivalent here yet: search, pins and stars, threads, placing calls, room details and settings, reminders. Typing, presence and complete history are not there yet; view-once and disappearing content is never kept.

**Packaged**: `desktop-whatsapp.yml` builds the helper on the three platforms with its licence notice, and every desktop package carries it beside the app (`scripts/package-*.sh`, `appimage-build.sh`); `whatsapp::locate()` also looks under an AppImage's root, like `rv-voice`.

SwiftUI: missing (the FFI filters WhatsApp accounts out of the shared keychain index).

## Mobile

Partial, Android only; designed in [the Android design](../../docs/WHATSAPP_ANDROID.md). The engine is the desktop helper's Go code built by Gradle as a C shared library (`apps/desktop/whatsapp/mobile`, `librv_whatsapp.so` per ABI, Go needed on the build machine) and loaded through JNA by the Expo module `apps/mobile/modules/whatsapp`: `WhatsAppEngines` keeps one engine per state under `noBackupFilesDir/whatsapp/`, its key wrapped by an Android Keystore key, outliving JS reloads and account switches; frames reach JS as `frame` events (proved on an emulator by `WhatsAppEngineTest`).

- **Account.** `kind: 'whatsapp'`, `baseUrl = whatsapp://<state>`, `userId` = `username` = the own JID, no token (`lib/provider.ts`, `lib/sessionTransport.ts`: nothing to resume; logout is the engine's `logout`, then `forget` erases state and key, `providers/whatsapp/unlink.ts`). The rail names it WhatsApp and does not poll it (`ui/serverRail.tsx`).
- **Linking** (`app/whatsapp-link.tsx`, a native form sheet). WhatsApp is one of the sign-in screen's server types; choosing it opens the sheet. A phone number gets a pairing code (`pair_phone`), shown `XXXX-XXXX` with Open WhatsApp and Copy; the QR, for another phone, is drawn in native views (`ui/qrCode.tsx` `TextQrCode`). Leaving the sheet before WhatsApp names the account erases the attempt (checked on the emulator).
- **Projection** (`providers/whatsapp/projection.ts`, tested). Frames become the shared tables: a room (`d`, or `p` for a group) and a subscription per chat, named from the `names` frame, with its newest message and unread count; messages with their author's name, attachments and deletions in words (`wa.kind.*`), edits dated, reactions as shortcode chips (`shortcodeOfUnicode`, `lib/emojis.ts`, mine under my username), the sender's link preview as a `urls` entry. Writes are coalesced into one transaction per burst. Each attach asks for a `replay`; the engine's closing `replayed` frame lets the projection drop the chats it did not bring back (`purgeMissingRooms`).
- **Provider** (`providers/whatsapp/index.ts`, `ui/sync.tsx`). Attaches to the engine, sends texts (WhatsApp-style ids), reactions, edits, deletions and reads as engine commands; a refused send is a toast. Online only while the app is in front, as on desktop.
- **Media** (`lib/whatsappFiles.ts`, tested). Received attachments are the timeline's native attachments (`NativeAttachment`, as Vibez's): their path `/api/v1/files/<base64url of the message id>` goes through the native file registry (`lib/nativeFiles.ts`), whose source sends `download` and waits for the engine's `file` frame, a path under its own folder. Sent ones go through the provider's file queue: the picked file is copied under the cache's `whatsapp/outgoing/` and sent with `upload` (100 MB); a note recorded in the composer (AAC in MP4) is first converted to Opus in Ogg by Android's codecs and muxer (`WhatsAppVoice.kt`, Android 10 and later, `WhatsAppVoiceTest`), so WhatsApp plays it as a voice note; before, it goes as an audio file. A file shows once WhatsApp has it (no progress meanwhile).
- **Photos.** Sent inline by the engine, written as `<cache>/whatsapp/<state>/photos/<jid>-<version>.jpg` (the version a digest of the bytes, the old file removed) before their version reaches the rows: a chat's on its room (`avatarEtag`), a person's in `users` (by uid), whose username is the person's WhatsApp name since the timeline names authors by it. `avatarUrl` maps them to those files.
- **Notifications** (`WhatsAppNotifier.kt`, `WhatsAppNotifierTest`). Posted by Kotlin from every engine's frames, so with or without JS: a `MessagingStyle` conversation per chat (id from `whatsapp:<state>:<chat>`, channel `whatsapp_messages`), named from the `names` frames, opening `rocketvibe://room/<jid>?host=<state>`, with Reply and Mark as read (`WhatsAppActionReceiver`, which starts and connects the engine when the process had none, within its ten seconds) and cancelled by a `chat` frame at zero unread. Nothing is notified before the engine's first `replayed` or between `reload` and `replayed`, nor my own, deleted or day-old messages, nor anything while the app is in front.
- **Background reception** (`WhatsAppService.kt`). WhatsApp sends a linked device no push, so only a live connection brings messages with the app closed. Per account, the notification settings' "Receive in the background" (after the notification permission) adds the state to `WhatsAppBackground` (preferences) and starts a foreground service of type `remoteMessaging` (API 34+) that starts those engines and stays under a quiet `whatsapp_background` notification whose Stop turns it all off; `WhatsAppBootReceiver` restarts it after a reboot or an update; unlinking removes the state. Off, the engine lives as long as the process does, and messages arrive at the next opening.
- **Replies and typing.** A reply carries the quoted message as the timeline's quote block (`message_link` `wa-reply:<id>`, author, text from the cache when it has the message, else the text the reply carried); the composer's Reply (capability `quotes`) sends `[ ](<permalink>?msg=<id>) text`, whose id `splitReply` (`providers/whatsapp/index.ts`) turns into the engine's `reply`. Typing frames become the room screen's `user-activity` events through the listener's `onEvent`, named from the projection; my typing goes through `Provider.setTyping` (`app/room/[rid].tsx` uses it when there is no native runner), said again every 10 s while it lasts. The message menu drops threads, pins and stars and keeps edit and delete to my own messages within WhatsApp's windows (`whatsappActions`, `lib/messageActions.ts`); the room header hides marked messages (`marks: false`).
- **New conversations.** The list's New conversation (`app/search.tsx`) asks `Provider.searchPeople` when the provider has one: the engine's `search` (contacts and groups by name, a typed number WhatsApp confirms) answered by a `found` frame. Opening a result calls `openOrCreateDm(name, jid)`, which lists the chat before its first message (`WhatsAppProjection.startChat`, named as found) so its room screen has a row; a later replay that does not bring it back drops it, as the desktop does.
- **Sending files** (`providers/whatsapp/files.ts`, tested). Each file is a row of the `uploads` table the room screen draws: sending from the `upload` command until the engine's `message` (mine) or `sent` frame for its id, failed with Retry and Discard on a refusal naming it; rows a killed process left sending go again on the next connection, `send_already_recorded` counting as sent.
- **Licence notice.** `build-android.mjs` writes `rv-whatsapp-licenses.txt` (every Go module from `go list -m -json all`, whatsmeow first) into the module's generated assets; Settings > App > Open-source licences (`app/licenses.tsx`) reads it through the module's `licenses()`.
- **Owed**: nothing of the desktop's feature set; live-checked: the service and its notification on the emulator, not yet a message notified with the app closed.
