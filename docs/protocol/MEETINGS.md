# Native Jitsi meetings (P20 / J4)

The server and the Rust / TypeScript transports are available. GTK and SwiftUI
wire up the existing room / profile buttons, cards and call windows.
Mobile remains to be wired; its native call client capability stays disabled.
Qualification against a real Jitsi service and the installed applications remains open.

## Operator configuration

`RV_JITSI_CONFIG_FILE` designates a regular, private JSON file (0600 on Unix),
of at most 16 KiB, containing `url`, `app_id` and `secret`. The URL is an HTTPS
origin, optional port, without credentials, path, query or fragment. The secret
holds 32-1024 bytes and must be randomly generated by the operator.
It is shared with the Jitsi validator, never stored in PostgreSQL nor sent
to the client. An invalid configuration stops startup without printing its value.
Without configuration, discovery announces `calls: false` and authenticated
commands fail with `503 calls_unavailable`.

Example of the shape, to be replaced in a private file outside the repository:

```json
{
  "url": "https://meet.example.org",
  "app_id": "rocketvibe",
  "secret": "REPLACE_WITH_A_RANDOM_SECRET_OF_AT_LEAST_32_BYTES"
}
```

The service must enable HS256 JWT authentication, the exact application identifier,
the audience `jitsi`, refuse missing tokens and verify the conference name
in the MUC component. The `sub` claim is the domain of the origin,
without its port. Tenant / proxy origins with a path are not supported
by this configuration. Sources: [official Jitsi token contract](https://github.com/jitsi/lib-jitsi-meet/blob/master/doc/tokens.md),
[official Docker configuration](https://github.com/jitsi/docker-jitsi-meet/blob/master/env.example).

## Routes and identity

The routes use the usual RocketVibe bearer and the private-delivery checks.
An administrator without membership does not obtain the address of a private call.

| Route | Intent / result |
|---|---|
| `POST /api/v1/rooms/{room}/meetings` | `StartMeeting`: operation, membership version, epoch; returns `Meeting` |
| `GET /api/v1/meetings/{id}` | Metadata accessible to current members |
| `POST /api/v1/meetings/{id}/join` | `JoinMeeting`: membership and epoch; returns `MeetingJoin`, private URL and token expiry |
| `POST /api/v1/meetings/{id}/end` | Same scope; creator, owner or moderator; idempotent closure |

The membership version is that of `ReadState.membership_version`, common to the
mobile and desktop caches. The permission to start follows the room's write
rights. A read-only member can join an existing call. Removal,
re-membership and restoration refuse old intents. A new
origin / identifier configuration does not reuse the meetings of the old one.

## Start and duration

Transactions lock account / session, room, membership and epoch. Concurrent
starts of a room find a single active conference, with a random opaque
name, valid for two hours. A single structured `call_started` activity
containing the meeting identifier is published in the journal.
The same operation ID finds its result, even after a restart, expiry
or end of the meeting; it does not create another call. Reusing the ID in another
scope is refused. Receipts are durable; 256 new operations per account
over 24 h are allowed, without evicting old receipts. A new operation
can create a new meeting when the previous one has expired or ended.

## Token and revocation

Each entry checks the account, session, membership and epoch again.
The HS256 JWT is limited to one exact conference (`room`, never `*`), to the domain,
the application and the audience. It lasts at most 120 seconds, without exceeding the
end of the meeting's validity. The user context contains the UID and the display
name; it grants no moderation privilege. A new token is issued
on each entry and appears in no message, journal, receipt or shared link.

The private URL carries the JWT in `?jwt=`, in accordance with the Jitsi web client.
Responses are `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
A delivery keeps the access locks and rechecks the meeting state until
the HTTP body is submitted, with the usual bounded lease. End of call, removal and
revocation cannot overtake a delivery that has already been accepted.

Closure blocks new tokens. It **does not revoke a JWT already
delivered**, valid until its expiry, and does not automatically expel
connected participants. Jitsi expulsion / moderation and its behavior at
expiry remain to be qualified against a real service. The E2EE encryption
of messages constitutes no guarantee of encryption of the call media.

## Evidence and exit still open

The desktop and mobile stores save a start intent per room before HTTP;
the next click reuses the same ID after a lost response or a restart.
No call is started automatically when the application returns. Confirmation
and definitive refusal remove only the intent concerned. Removal, re-membership,
epoch change and account closure purge the intents.
Private URLs remain temporary. Room scope, conference, HTTPS origin,
short expiry and absence of redirect / credentials are verified before
handing over to the call window. Shared links cannot contain a JWT.
A late response after an account change, navigation or membership is refused.

The core's HTTP tests cover lost response, real reopening of the SQLite,
replay of the same start, meeting of another room, removal and restoration.
The store tests cover re-membership and late acknowledgement; those of the URLs
refuse different conference / origin, added query and excessive expiry.
The GTK widget receives the native activity and produces the join / info events
with the meeting ID in its existing buttons. These benches do not validate the media.

The real PostgreSQL / HTTP tests exercise concurrency, receipts after restart,
absence of admin bypass, read-only, removal / re-membership, epoch change,
expiry, idempotent closure and refusal of new entries. A join HTTP body
is held during a concurrent closure, then consumed: the closure
waits for its delivery and the following join is refused.
The quota refuses a new operation without blocking the retry of a receipt, the
read, the entry or the end. Maintenance and the passage of time do not remove
receipts; a revoked session can no longer receive a JWT.

The real mobile transport authenticates against the same server and replays its
start. An independent Node verifier checks the HS256 signature, the scope
claims and the lifetime of the Rust JWTs; no token is printed.
The same bench mounts the mobile provider and the binding used by the current screens:
it receives the activity in `messages.call_id`, loses a confirmation,
reopens the on-disk SQLite and resumes the same ID on the next click. A reconnection
does not start a call. The helper refuses a URL delivered after the account was unmounted;
a detached native session never tries the Rocket.Chat endpoints.
The existing room / profile buttons, card and WebView follow this
binding, with view / membership guards and the WebView origin kept. A profile's
new DM waits for its membership coming from the journal. The camera / microphone settings
use the [official Jitsi](https://github.com/jitsi/jitsi-meet/blob/master/react/features/base/config/configWhitelist.ts) options.
The targeted tests cover double tap, quota, permanent refusal, removed
configuration, changed epoch and closure during entry. The Rocket.Chat probes
remain memoized per account client; an outage / a quota remain retryable.
These benches do not yet prove acceptance / refusal by Prosody, the media,
moderation, nor the journeys in the installed applications. P20 / J4 remain open.
