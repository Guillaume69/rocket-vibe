# RFC 0002: Native encryption and RocketVibe history

| Field | Value |
|---|---|
| Date | 3 October 2026 |
| Status | J4 working specification; isolated vault, server opaque journal and protected pages in the HTTP worker, no capability enabled |
| Reference | RFC 0001 §13, P18 / P19 |
| Clients | Providers of the current mobile, GTK and SwiftUI apps |

## Working decision

Evaluate MLS 1.0, [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html),
with OpenMLS in Rust for the new encrypted groups. The `rc.v1` and `rc.v2`
formats keep their compatibility reader for Rocket.Chat and imports. A room has an
explicit format; no ciphertext is guessed from its content and no send falls back
to plaintext if a key is missing.

The first prototype uses OpenMLS 0.9.0 and its RustCrypto provider 0.6.0, stable
versions verified on crates.io. Single suite:
`MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (0x0001). The engine will delegate
the MLS operations to this library; no ratchet or group exchange is
reimplemented in the API. The engine is now wired to the server and to the existing
interfaces, behind a production E2EE capability that is disabled.
The existence of a library is not an audit of our integration.

A shared Rust engine avoids two diverging native crypto implementations.
It is reachable from the desktop core and from a native mobile bridge limited to
key / message operations. The current lock, room and profile screens remain the
entry points. The Android / Hermes bridge, its two ABIs and the real Keystore
pass in CI on an emulator. OpenMLS reports tests on Linux / Windows / macOS and
Android builds; that does not qualify our app.
[Project source](https://github.com/openmls/openmls).

## Identities and devices

An account has an E2EE signing identity generated by the client. Each device has
its MLS key and a certificate signed by that identity, bound to the immutable
account / device / instance identifiers. A renewed HTTP session keeps the device
identity; a login on another installation creates a new one. The sign-in password
is not an E2EE key.

A new device requires the approval of an already authorized device or a distinct
E2EE recovery secret. A stolen bearer or an administrator cannot sign a
certificate. KeyPackages are signed, time-bounded, consumed once and bound to the
device; publishing them does not grant access to a group.

A correspondent's identity is pinned locally and verifiable by fingerprint out of
band. The first unverified contact remains vulnerable to a substitution by the
identity service; the UI must say so. A root change suspends the addition of keys
until a new explicit verification. A valid signature from the HTTP service never
replaces this verification.

Adding a user to the group requires an action by an authorized member, with the
identity and the recipient list presented before signing. A member's new devices
must present their valid delegation. Server notifications alone do not trigger the
admission of a new E2EE root. The isolated module [`identity`](../../crates/rv-crypto/IDENTITY.md) implements Ed25519
roots, bounded certificates, explicit pins, out-of-band comparison and monotonic
revocations. The admission of a KeyPackage validated by OpenMLS requires the
certified leaf key and its exact local approval. An old confirmation cannot
restore another incarnation; a changed root requires the previous and new
fingerprints to be confirmed and erases the approvals.
Nine tests cover substitution / expiry / revocation / persistence,
including a public vector also verified independently under Node / OpenSSL.
[Signed request and exact grant](../../crates/rv-crypto/ENROLLMENT.md) are
implemented in the isolated engine: new key / incarnation, proof of possession,
opaque confirmation, Grant bound to the request and replayable private receipt.
Eleven tests cover refusal / reopening / lost checkpoint, expiry / clock rollback,
substitutions / limits and a real KeyPackage; the request / Grant vector passes
Rust and Node / OpenSSL. [Root recovery](../../crates/rv-crypto/RECOVERY.md)
by a random 256-bit code, an XChaCha20Poly1305 packet and restoration into a new
vault is implemented. An exact receipt allows resumption without erasing a leaf
created since; eight tests cover refusal / tampering / reopening.
UI ceremony, delivery, control delegation,
archive recovery and the room list remain to be integrated; a bare MLS `BasicCredential`
does not provide them. If the
private root is compromised, revoking a single leaf is not enough: the
root must be replaced with a new out-of-band verification.

## Group, ordering and removals

An MLS leaf represents a device, and several leaves may belong to the
same user. The group is bound to the instance, the data epoch, the
room and a random incarnation; a removal followed by a return does not reuse
an old authorization. Messages also authenticate the operation ID,
the author / device, the content type and the conversation / thread scope.

The server acts as delivery and keeps the binary MLS messages, the public trees
and the Welcomes intended for authorized devices. It serializes
commits per group / expected epoch, with a durable operation receipt and a
queryable result. Welcome and commit are published in the same transaction; the
client merges its prepared commit only after confirmation of its acceptance.
Peers verify signatures, recipients and policy before merging.

Removing a member or revoking a device immediately invalidates its HTTP access
and blocks new encrypted sends from the old list. An authorized device
must produce the removal commit before resumption. If no device able to
do so is connected, the room waits; the server holds no key with which to
rotate the group. A member who was already a recipient keeps the contents and
keys received earlier. Remote deletion cannot erase them on their side.

Two concurrent commits are not merged blindly. The loser observes the
receipt and the new state before proposing another commit. An accepted ciphertext
is replayed identically; an obsolete operation that is definitively refused allows
re-encryption under a new operation. Automatic loops are
bounded and stop on a change of account, group or membership.

The service can hold back, reorder or refuse deliveries: MLS does not guarantee
availability. Transcript discrepancies must suspend the group and
produce a diagnostic without secrets. The application delivery and
identity policy also falls under the [MLS architecture, RFC 9750](https://www.rfc-editor.org/rfc/rfc9750.html).

### Current validity and historical signatures

Reading the journal for an unchanged admission distinguishes signature
authentication from the current authorization to send. Expiry alone does not
remove the authenticity of the signatures of an old MLS certificate / packet.
The reader must remain active, with a current local certificate and the same key
identity after renewal. Peers remain subject to the explicitly approved pins
and the known revocations as they currently stand; a changed root, unknown device,
invalid signature or future certificate suspend new decryption.

Historical signatures prove neither their creation date nor that their
author then held a server authorization. Delivery metadata
does not become proof of a date. Send / retry / publication / new
admission keep the current-validity checks on the client and server side.
The reader's clock is not replaced by a date chosen by the signer.
Private contents already accepted keep their personal authorization for
replay; archives and history after revocation are a distinct
policy. [Implementation and proofs](../../crates/rv-crypto/JOURNAL.md).

A joint compromise of the signing keys and the secrets of an old
epoch may allow contents attributed to that epoch to be forged.
Historical authentication therefore does not prove that they precede the expiry
or a revocation. This limit remains subject to independent review.

## Persistence, recovery and history

MLS state, key consumption, outgoing ciphertext and the processing cursor
must be committed together before network delivery or presentation of the plaintext.
A crash must not reuse a send generation nor present a message
whose consumption is not durable. The engine must be able to prepare a
transition in transactional storage without mutating the active state on a refusal.
The prototype finds that the refusal of a tampered message can consume a
receive key: restoring the storage alone without reloading the group in memory is
insufficient. It also finds that the old epoch remains able to send during a
prepared commit; our application guard must therefore explicitly forbid sending.
An older restored database is treated as a loss of state: new device
and new Welcome, never a silent resumption of the old send keys.

Private storage must be encrypted and authenticated with a key protected by the
keyring / Keystore. WAL, backups and temporary files must follow the same
policy. OpenMLS trusts its storage; a plain SQLite table
does not meet this requirement. [OpenMLS persistence contract](https://book.openmls.tech/user_manual/persistence.html).

### Implemented storage foundation

The isolated crate [`rv-crypto`](../../crates/rv-crypto/README.md) implements a
SQLite row containing the MLS provider and the operation records, sealed
together by XChaCha20Poly1305. 32-byte key, 24-byte OS random nonce,
AAD `(rocketvibe-mls-vault-v1, scope, revision)`; JSON document bounded to 16 MiB.
The scope comprises instance, generation, account, device and incarnation.
[RustCrypto AEAD 0.10.1](https://docs.rs/chacha20poly1305/0.10.1/chacha20poly1305/).

The provider is rebuilt for each immediate SQLite transaction, then
destroyed. MLS consumption, outbox ciphertext and private receive data
share the durable commit; a refusal rolls back all changes. The parent
must be private; exclusive creation and checks of Unix permissions / links,
encrypted WAL and `synchronous=FULL` are enforced. Windows ACLs and real
durability after a power cut remain to be qualified.

A public checkpoint `(revision, SHA-256 digest of the AAD / nonce / ciphertext)`
is stored with the key in the keyring, outside the database. Each new
checkpoint blocks the following reads / transactions until the adapter has
confirmed its protected write. No result can be published before
that confirmation. The adapter's OS lock must cover read, commit,
write and verification, including when the requester is cancelled, to
prevent a late keyring write from restoring an old checkpoint.

If the process dies after the SQLite commit but before the checkpoint is written,
only the successor exactly one revision further can be resumed: its authenticated
document must contain the previous protected checkpoint. Resumption
stays blocked until the new marker is protected. An earlier head, another
scope, a tampered predecessor or an incomplete file allow neither sending nor
silent recreation.

The coordinator `protected::Manager` implements this lock on the owned worker,
the predecessor verification and the re-reading of the checkpoint after the write.
The protected entry is bound to the canonical directory; a copy of the database
under another lock cannot fork the send state of the same device.
Explicit initialization saves the key first; its resumption before the marker
accepts only an empty authenticated genesis. An incomplete file requires explicit
removal and then a new incarnation. Removal saves a keyless tombstone
before removing the files, and never reactivates the old incarnation.

The optional keyring 3.6.3 adapter has native backends explicitly chosen
for Linux / macOS / Windows, in a service distinct from the existing sessions.
[Keyring API and features](https://docs.rs/keyring/3.6.3/keyring/).
The real Linux Secret Service is verified with new processes and buses,
concurrent lock, forced stop after commit / before checkpoint, resumption and
removal. The [Android bridge](../../crates/rv-crypto-mobile/README.md) now provides
a vault protected by Android Keystore, with Kotlin bindings and a system lease
tested on an emulator. The mobile association now uses the ceremony
in Rust shared with the desktop and the existing settings: fingerprint compared,
opaque consent, public codes and original receipt recovered after reopening.
The Android test passes the real ceremony with no key export; mobile groups and
conversations, keyring backups,
installed Windows / macOS and power cuts remain open.

The durable vault does not yet claim forward secrecy of the storage:
an old encrypted copy in the WAL / backup remains decryptable with the compromised
durable key. Restoration detection prevents its reuse,
without erasing it. Rotation / destruction of the storage keys and the policy on
copies are a J4 condition, distinct from the recoverable archive.

Fourteen vault tests, including an MLS exchange after a disk reopening and two processes
killed before / after commit, plus the real keyring pilot verify this
foundation; nine additional tests cover the certified identities, eleven
the device addition and eight the root recovery, 42 scenarios in total.
The vault is not yet opened from the interfaces; its worker is
wired to the desktop provider core with a session guard. The [server public directory](../protocol/E2EE_DIRECTORY.md)
consumes the extracted verifiers without private keys: certificates / requests /
grants, publication of real KeyPackages and persistent receipts are available.
The [server groups batch](../protocol/E2EE_GROUPS.md) adds a signed list, CAS on
revision / epoch / parent, atomic consumption of packages and targeted Welcomes,
with real MLS add / join / removal tested against PostgreSQL.
Local verification / admission and the vault / outbox coordinator are delivered.
The private worker is also exercised on the real Rust / PostgreSQL server:
package publication, admission and rotations by both peers, lost responses
and reconciliation of receipts without a new POST. The external checkpoint
of this bench is simulated. Message delivery, planning / interfaces and
qualifications remain open; E2EE stays disabled.

### Archive and recovery

MLS is not a recoverable archive: the application keys are consumed.
The author cannot decrypt their own send again from the ciphertext alone.
A new Welcome does not automatically make the old history readable.
[OpenMLS message behavior](https://book.openmls.tech/user_manual/application_messages.html).

To satisfy the history requested by RFC 0001, a distinct E2EE archive
will be needed, with explicit recipients and sharing authorization. A recoverable
archive key deliberately preserves access to the archived messages:
no forward secrecy will be claimed for this archive. Recovery
readmits a new device; it does not restore an old MLS state in order to send.
New member, new device and former member are not equivalent recipients;
the history rules are fixed before implementation.

The [archive policy](../protocol/E2EE_ARCHIVE.md) now fixes these rules:
separate membership periods, explicit recovery for a new device of the
same account, no automatic prior history for a new member and
retention of the documents already authenticated after their author is removed.
It distinguishes local copies from authorizations to download again.
The document format and the local catalog are extended below; the
recipient envelopes and their qualification remain to be delivered.

A [first archive document format](../protocol/E2EE_ARCHIVE.md#first-format-immutable-document-v1)
implements AEAD, signature and binding to the original. The vault keeps immutable
blocks and an observation catalog bound to the admission. The shared
desktop / Android projections read a separate index of the verified journal pages,
including thread roots / counters and the last page after the cache is forgotten.
The 70-message bench, migration / prefix and HTTP worker pass; synthetic
receipts and installed qualification remain distinct. The hot cache now evicts
settled bodies automatically and quote sources read the verified index. The operation
/ load registry, admission of portable packets,
transport, key envelopes / backups and review remain open.
The **account root** backup
is implemented separately: random OS code, AAD bound to the root / backup ID,
encrypted private seed and new restoration with an exact replay receipt. It does not
recover any ratchet, archive key, pin or historical file. An old code
and an old copy keep access to the root; changing the code does not
revoke it. A root compromise requires replacement and verification.
HTTP publication / settlement and backup / restoration ceremonies are
wired to the existing Android / GTK / SwiftUI settings. The CI runs for the server,
Swift models, GTK under Xvfb, macOS and Android / real Keystore are green for
this batch. Installed qualification, archive recovery and review remain open.
Without a secret or an authorized device, lost history remains unrecoverable.

## Data and compatibility

Text, mentions, cards, quotes, captions and file descriptors live
in the encrypted payload. The server sees the routing metadata, sizes and
recipients that it needs. Search, previews and notification content are
built locally after decryption. A lock purges private memory / indexes;
it does not claim to remove the copies already exported by the user.

Streaming file encryption must use an established, authenticated format,
with file keys only in the E2EE payload. Its choice and its cross-app vectors
are a dedicated batch; the MLS prototype does not cover files.

For P18, the historical blobs, private / room envelopes, algorithms,
parameters and UIDs used as salt are imported opaque. No server receives
the secret to convert the history. Clients open these contents with the existing
readers. Switching to new MLS sends creates a new incarnation
with consent and visible history boundaries, without rewriting the blobs.
