# RFC 0003: Bots on the RocketVibe server

| Field | Value |
|---|---|
| Date | 8 October 2026 |
| Status | First layer implemented on `feature/bots`: server, mobile, GTK and SwiftUI (protocol: [BOTS.md](../protocol/BOTS.md)) |
| Reference | RFC 0001 §11 (accounts and permissions), `docs/protocol/INTEGRATION_CARDS.md` |
| Clients | Providers of the current mobile, GTK and SwiftUI apps (RocketVibe server only) |

## 1. Summary

A **bot** is a non-human account owned by a person. It authenticates with
**API keys** instead of a password, and acts through the existing API inside a
list of **scopes** its owner grants. It is a member of rooms like anyone else,
posts plaintext messages and integration cards, and listens to the same journal
and socket as the apps. Every person may own bots when the instance allows it;
administrators always may.

This is the first layer of an automation platform. Bot-declared slash commands,
outbound events over HTTP, interactive messages (buttons, forms) and a workflow
engine built as an internal bot are later layers of the same RFC (§10). Rocket.Chat
accounts are untouched: on a Rocket.Chat server the feature is `n/a`.

## 2. Goals and non-goals

Goals:

- A person creates a bot, gives it a name, a description and scopes, and issues
  one or several keys (rotation without downtime), each shown once.
- A bot can never do what its owner could not: no administration, no account
  security, no encrypted rooms, only rooms it was invited to or public ones.
- Everyone can tell a bot from a person: a `bot` flag on every `User`, a badge in
  the three apps, the owner shown on the profile.
- An administrator turns bots for everyone on or off, sees every bot, disables
  any of them.

Non-goals of this first layer: bots in encrypted rooms (§8), anonymous incoming
webhooks (still refused, `INTEGRATION_CARDS.md`), a marketplace or app directory,
OAuth installation of a third party's bot into someone else's workspace.

## 3. Instance policy

`instance.user_bots` (boolean, **false by default**). When false, only
administrators create bots. When true, every active account may. Turning it off
later creates nothing and removes nothing: existing bots keep working, an
administrator disables them one by one if needed.

- `GET /api/v1/admin/settings` and `PATCH /api/v1/admin/settings` with
  `{user_bots}`, administrators only, audited as `instance.settings`.
- CLI: `set-instance --user-bots true|false`.
- `AccountPermissions.create_bot` tells the apps whether to offer creation:
  `admin || user_bots`.

Limits: 10 live bots per owner (administrators included), 10 creations a day per
owner (deleted bots included: deleting retires a username, which must not become
a way to retire names at will), 5 live keys per bot.

## 4. Data model (migration `0052_bots.sql`)

- `instance.user_bots boolean NOT NULL DEFAULT false`.
- `bots(user_id PK → users, owner_id → users, description, scopes text[],
  created_at, operation_id, UNIQUE(owner_id, operation_id))`. Mutations reuse
  the receipts of in-app administration (`moderation_commands`, per acting
  account and operation). The bot is a
  `users` row: username, display name and avatar work everywhere unchanged. Its
  `password_hash` is unusable and sign-in ignores bot accounts outright (they
  take the dummy-hash path, so timing does not reveal them).
- `bot_keys(id PK, bot_id → bots, device_id UNIQUE → session_devices ON DELETE
  CASCADE, label, hint, created_at, expires_at)`. A key **is** a session: one
  `session_devices` row (label = key label) and one `sessions` row whose
  `token_hash` is the SHA-256 of the full key. Authentication, `lock_active`,
  read proofs, cursors and tickets therefore work unchanged. Revoking a key
  deletes its device row; the cascade removes the session and the key.
- A key without expiry gets `expires_at` far in the future; `sessions` keeps its
  `NOT NULL`.
- Triggers keep the invariants whatever the path: a bot is never `admin`, a bot
  owns no bot, and a session for a bot account must belong to one of its keys
  (no sign-in, invitation or recovery session).
- Trigger: when an owner becomes `disabled` (deactivation or deletion), its bots
  become `disabled` in the same transaction. Re-enabling the owner does not
  re-enable them.

## 5. Keys and the scope gate

Key format: `rvb_` followed by 64 lowercase hexadecimal characters (68 bytes).
`auth::bearer` accepts it and hashes the **whole** string, so a key stripped of
its prefix, or a person's token given the prefix, matches nothing. The
prefix makes a bot request recognisable before any database access.

A route layer (`bots::gate`, run after routing so it sees the matched path) does
nothing for a person's token. For a key it resolves the bot's scopes (one
indexed query) and admits the request only if `(method, matched path)` is in the
allowlist below under a granted scope. Everything else answers **403
`bot_scope_missing`** (route allowed to bots, scope not granted) or **403
`bot_forbidden`** (route never open to bots). Deny by default: a new route is
closed to bots until it is listed.

| Scope | Routes |
|---|---|
| (always) | `GET /me`, `GET /me/profile`, `GET /me/permissions`, emoji catalogue and images, `GET /avatars/{id}`, `GET /bots/reference`. The bot's own profile is read-only to its keys: its owner edits it |
| `rooms:read` | rooms list and details, members, permissions, history, threads, pins, files, snapshots, changes, socket ticket |
| `messages:write` | send, reply, edit and delete its own messages, typing |
| `files:write` | upload preparation, transfer, completion; completing posts a message, so it also needs `messages:write` |
| `reactions:write` | add and remove reactions |
| `rooms:join` | public directory, join a public room, leave a room |
| `users:read` | user directory, lookup, profiles |
| `dm:write` | open a direct conversation |

Never open to a key, whatever its scopes: sign-in and session routes (renew,
logout, sessions), `/me/*` security routes (password, factors, email, reauth),
push registration, every `/e2ee/*` route, `/admin/*`, `/bots/*` but the
reference (a bot does not manage bots), voice and calls, reports, room creation
and room settings, its own profile edits.

The socket opened with a ticket carries no bearer and is not gated: the ticket
was issued to the key under `rooms:read`, and the socket asks again on every tick
whether the bot still holds it, closing when the scope is withdrawn.

## 6. Managing bots (person tokens only)

| Route | Effect |
|---|---|
| `GET /api/v1/bots` | My bots; `?all=true` lists every bot for an administrator |
| `POST /api/v1/bots` | `CreateBot{operation_id, username, display_name, description, scopes}` → `Bot`. Requires `admin \|\| user_bots`; username rules of any account (identifier, not reserved, not retired, unique) |
| `PATCH /api/v1/bots/{id}` | `UpdateBot{operation_id, display_name?, description?, scopes?}`, owner only. A scope removed applies on the next request |
| `PUT`/`DELETE /api/v1/bots/{id}/avatar` | The bot's photo, owner only |
| `DELETE /api/v1/bots/{id}` | No body, idempotent. Owner or administrator: the account is tombstoned like a deleted user (username retired), keys revoked, memberships left |
| `GET /api/v1/bots/{id}/keys` | `[BotKey{id, label, hint, created_at, expires_at, last_used_at}]`, owner or administrator |
| `POST /api/v1/bots/{id}/keys` | `CreateBotKey{operation_id, label, expires_in_days?}` → `BotKeyCreated{key, info}`, the only time the key is shown. Owner only, after a recent sign-in (`factors::recent`, the rule of device revocation) |
| `DELETE /api/v1/bots/{id}/keys/{key}` | No body, idempotent: revokes one key, owner or administrator |

An administrator oversees every bot (lists them, their keys, revokes keys,
deletes bots) but never acts as one: keys, scopes and the profile are the owner's
alone, so administration opens no way into the private rooms and direct
conversations a bot belongs to. Administrators also disable or re-enable a bot
through the existing user administration (`PATCH /admin/users/{id}`); as for a
person, a policy change revokes its sessions, hence its keys. A bot is refused the
admin right (409 `bot_privilege`), and re-enabling one that is a member of an
encrypted room (409 `bot_encrypted_room`).

Every change is audited (`bot.created`, `bot.updated`, `bot.avatar`,
`bot.deleted`, `bot.key_created`, `bot.key_revoked`) with the acting account.

## 7. What others see

- `User.bot: bool` (omitted when false) on every author, member, profile and
  live entry. The apps draw a "BOT" badge next to the name in the message header,
  member lists and profiles.
- `UserProfile.bot_owner: Option<User>`: the profile of a bot says whose it is.
- `Bot` and `BotKey` are visible to their owner and to administrators only.

## 8. Encrypted rooms

A bot has no crypto device, and an MLS plan must represent every member
(`crates/rv-crypto-public/src/groups.rs`, `E2EE_GROUPS.md`). Today, adding a
deviceless account to an encrypted room is accepted and then blocks every
encrypted send of the room (`needs_rekey` with no valid plan). The server
therefore:

- refuses to add a bot to a room that has an MLS group, by invitation, join or
  operator: **409 `bot_encrypted_room`**;
- refuses a group transition (genesis or change) while a bot is a member:
  **409 `crypto_bot_member`**; the apps word it and do not offer encryption in
  such a room.

A direct conversation with a bot stays plaintext, as every conversation does
until its members create a group. Bots inside encrypted rooms would need the bot
to run `rv-crypto` with its own certified device (a visible member holding its
own keys, not the server): a separate, later chantier.

## 9. Abuse limits

Plain sends have no rate limit today. For bots: 60 new sends per minute per bot
(sends and replies; a replay of an accepted send is free) and 10 new direct
conversations per minute (reopening an existing one is free), in the `bot_windows`
table, answering 429 `bot_rate_limited` with `Retry-After`. A bot's photo spends
its owner's profile decode budget. Other budgets (message actions, search, live)
already apply per user or device.

## 10. Later layers

1. **Bot commands**: a bot declares slash commands (scope `commands`); the
   catalogue merges them for the rooms the bot is in; `commands/run` delivers an
   invocation event to the bot and its answer comes back as a private note.
2. **Outbound events** over HTTP, signed, retried by a leased worker, for bots
   that do not hold a socket.
3. **Interactive messages**: buttons and forms in cards, rendered natively in the
   three apps, the submission routed back to the bot.
4. **Workflows**: an engine inside the server that acts as a bot, triggered by
   commands, schedules, joins and webhooks.
5. **Encrypted bots**: a crypto device for a bot through the SDK.
